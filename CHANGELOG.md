# Changelog

All notable changes to the GlimStone design language are documented here. Versioned independently of any app that adopts it.

## 1.7.0 — 2026-08-31

### ✨ Added

- **Reordering by dragging is a rule now, not an app's private invention.** Long press to arm (never a plain touch on a touch screen: it fights the list's own scrolling, and every attempt to tell the two apart by distance or direction gets one of them wrong somewhere), everything wiggles while armed because the wiggle is a MODE indicator about the LIST rather than about the row under the finger, the dragged row lifts with both `elevation` and `z-index` set, and the others move out of the way AS IT PASSES rather than on release, so the gap is always where the row would land. Plus the four things that are only obvious after building it: a drop that lands where it started writes nothing; rows reorder only within their own BAND, or the gesture can express an order the list cannot render and the store cannot hold; the target is computed against MEASURED row boxes, because a group header is taller than a row inside it; and the order is written whole rather than as a diff, so two clients dragging the same list merge orders instead of merging opinions about what moved.
- **When adding a gesture library would mean new NATIVE dependencies in a fragile build, the platform's own primitives are enough** — and the trade belongs in the code rather than in somebody's memory. A reorder gesture is not worth putting a build at risk for.

### 🔄 Changed

- **The version footer becomes an About card, and the old section is replaced rather than extended.** The footer was defensible: one quiet line, fixed to the window, on every settings tab without being implemented per tab. What it could not do only shows once you ask what somebody does NEXT with a version number — they report something, and page chrome has nowhere to put that. The card carries the versions, one sentence inviting a report, and two buttons: the repository, and a `mailto:` with the subject prefilled (no body, because a prefilled body reads as a form to fill in). **It is the one card in this language whose content is prose rather than an info bubble**, and that is a named exception rather than an oversight of rule 8: a bubble hangs an explanation off a control, and this card has no control to explain. Watch for the failure mode where both ship — the card AND the footer are each individually defensible, and together they are one number in two type sizes twelve pixels apart, which is what got reported the moment the card landed. Built across three surfaces of one product in a single round, which is also the check that it generalises.
- **A number field keeps its steppers, drawn by the app.** 1.5.1 dropped the native spinner and was right; it also dropped the affordance and was therefore incomplete, which took exactly one release and three words to find out (*"jetzt sind keine pfeiltasten mehr da"*). Two square controls in the page's own tokens, driven by `stepUp()`/`stepDown()` so the range lives in one place, each greyed out at its own end. **The general form: a rule that removes a native widget owes the replacement in the same breath, or the next release is a bug report.**

## 1.6.0 — 2026-08-31

### ✨ Added

- **The label engine — how much of a control's identity is shown: its text, its glyph, or both.** Four modes (`text`, `textGlyph`, `glyph`, `reactive`) across three independent surfaces (`buttons`, `sidebar`, `tabs`), each setting its own `data-labels-*` attribute on the root. Asked for as a real engine rather than a per-app switch (*"Kannst du die neuen button modi in GlimStone speichern. eine neue engine anlegen"*), and it earns the name the same way shape, colour and motion do: one input resolves to a token set, and nothing downstream knows which setting produced the value it got. `reference/controls.ts`, framework-free.
- **Three axes rather than one global switch, because the surfaces ask different questions.** A navigation rail reduced to glyphs is a *layout* decision — the rail narrows, the page widens. A button reduced to glyphs is only a *density* preference. One switch would force somebody who wants a compact rail to also accept unlabelled buttons, which is a question they were never asked.
- **Width stages are what make the engine usable, and they come first.** A control keeps the same width in all four modes, so switching mode never reflows the page — which means the width cannot come from what is currently rendered (a lone glyph is narrow) and has to come from the LABEL, present in every mode even when it is only the accessible name. Four stages derived from the label's length in visual units, CJK counting double; pure functions, known before first paint, rather than measurement after layout. **The `reactive` mode exists only because the stages already reserve the label's width** — the words arrive inside a box that was always that size. Build the stages first or do not offer that mode, or it reflows the interface under the pointer.
- **The stage comes from the CURRENT language.** Across a large locale set the same label grows by up to 3.4x — "Clear" becomes "Kijelölés törlése" in Hungarian. A single global stage per control makes every English and Chinese interface pay for the longest translation, permanently.
- **A derived stage is a floor; a group stage is exact.** `groupStage(labels)` is for controls that belong together visually but are rendered by different components, so neither can see the other's label. Both compute it from the same labels rather than one passing a width to the other — they agree in every language without a prop threaded through the markup, and keep agreeing when one of the two words is retranslated. Because it is applied exactly, it pads for the glyph, gap and padding that a text measurement cannot see.
- **A control in a hiding mode drops its gap (`gap: 0`).** A zero-width label is still a flex item, so the container's gap survives it and the glyph sits visibly off-centre in what is supposed to be a square button. Reported as *"das symbol ist nicht mittig"* and easy to misread as a centring bug in the glyph itself.
- **The shared glyph assortment**, `reference/glyphs.md`: one icon set across every app that speaks this language, so a folder is the same folder in all of them (*"Können wir auch eine glyph sortiment anlegen, damit alle meine apps die gleichen glyphen haben?"*). Names, sources, licences, and the meanings as a contract — an app that needs "delete" uses `IconTrash`, it does not pick a different bin. A list of sources rather than a folder of SVGs, for the same reason this repo ships tokens instead of components: an app generates its own file and can regenerate it, with no vendored artwork to drift.
- **Seven sizing rules, every one of them written down after a live review reported something "too big" or "too small" while every box on screen was already identical.** The headline: **what the eye compares is INK, not the box**, and **ink must be measured, never inferred from the viewBox** — a path's drawn extent and its viewBox have no necessary relationship. Then: normalise by cropping the viewBox rather than editing paths; match a pair on its shared dimension, which is width for two wide glyphs and height for a near-square one beside a wide one; **matching a pair to each other is necessary and not sufficient**, since a pair tuned only against itself can still be the smallest thing in a strip; **detail thinner than the raster disappears and scaling cannot fix it** (one unit of a 14-unit grid is 1.43px in a 20px box, so anything under ~1.5 units merges into its neighbour); and a plus or an X is shorter and thicker than the imported one, with the X drawn as the plus rotated 45° so the pair cannot drift.

### 🔧 Changed

- **"Two of these axes hand off to a named engine" is now "most of them."** Motion intensity had already gained one in 1.5.0 without that sentence being updated, and the label engine makes four. The count was wrong before this release, not after it.

## 1.5.1 — 2026-08-30

### ✨ Added

- **Never a native number spinner, for the identical reason as the native checkbox.** `<input type="number">` is fine and keeps everything worth keeping — min/max/step, the arrow keys, a phone's numeric keypad — but the two arrows the browser paints beside it come from the OS widget set, on their own background, and the only property that reaches them is `accent-color`, which recolours one part of a control whose geometry, ground and spacing still ignore every token here. Same excuse ("it is a native input"), same answer: the widget goes. Reported live on an adopting app's options page, and the second half of that report is the part worth keeping — *"die beiden pfeiltasten … haben einen dunklen hintergrund und der text ist zu nah an diesen pfeilen"*: they do not merely look wrong, they crowd the value, so a right-aligned field has its digits pressed against a widget from another design system.
- **The recipe names the STANDARD property, not only the WebKit one.** `appearance: textfield` plus `::-webkit-outer-spin-button`/`::-webkit-inner-spin-button { appearance: none }`. Firefox draws its spinner through a different pseudo-element, so a WebKit-only rule leaves those arrows exactly where they were — the same shape of half-fix as any other `-webkit-`-only appearance reset.

## 1.5.0 — 2026-08-30

### ✨ Added

- **The accent is two tokens now, because it was always doing two jobs.** `--accent` is the fill — a badge, a switch track, a primary button — and the ink on top of it is already computed, so the fill needs no adjusting for the theme: Sunflower on a white page with near-black text on it reads perfectly well. The new `--accent-ink` is the other job: the accent used AS a colour that gets read, on the page's own ground. That one does need darkening on a light ground, because gold text on white is unreadable at 11px whichever gold it is. Until now this was ONE token, darkened for the light theme — which reads as a sensible compromise and is not one: it makes the fill wrong in order to fix the text. An adopting app's light theme drew every badge, switch and filled button in olive-brown, and the report was flat: *"Die gelbe Akzentfarbe ist im hellen Modus ganz dunkel."* The general lesson is the one worth carrying: **a token doing two jobs will be wrong for one of them, and the tell is that one of the two consumers keeps getting reported.**
- **`--accent-ink` is DERIVED, not a second colour anybody picks** — `color-mix(in srgb, var(--accent) var(--ink-mix), black)`, where the theme sets `--ink-mix` to `100%` on a dark ground and `55%` on a light one (100% of a colour mixed with black is that colour exactly). The mix factor is a token rather than a literal for a concrete reason: `--ink-mix` is inherited from `<html>`, so every `--accent-ink` in the sheet is ONE declaration that is already correct in both themes. The first cut wrote the literal and needed a light-theme twin beside every rainbow rule — four selectors to keep in step by hand, which is the shape of a rule that drifts. Derived matters twice over: it follows a colour the user chose, which the old fixed light-theme constant never did (it only ever applied to the DEFAULT accent, so a picked yellow stayed unreadable), and it re-resolves on a theme switch that happens after the accent was applied. `applyAccent()` therefore deliberately does not compute it — writing it from JS would freeze it at whichever theme was in force when the colour was picked, which is the bug the split exists to avoid. Measured against white, the palest ground in this palette: Sunflower lands at 4.95:1 and all five accent presets clear 4.5:1; Sunflower also computes to `#8B6C0E`, within a shade of the `#8E6A00` the single token used to be, which is the check that this generalises the old rule rather than replacing it.
- **The trap that comes with it, and it is not obvious: a custom property whose value contains `var()` is substituted where it is DECLARED, not where it is used.** `--accent-ink: var(--accent)` written on `:root` computes against `:root`'s own accent and hands descendants that finished colour — so a `.glim-hue` subtree redefining `--accent` for its position would have taken the hue on every fill and kept the single accent on every piece of accent-coloured text. The rainbow, half applied, which is exactly the failure 1.4.0's position-on-the-container rule was written to end. `--accent-ink` is therefore redeclared inside `[data-rainbow] .glim-hue` (and its light mirror) alongside `--accent` itself. **Anything added beside `--accent` in the theme blocks has to be repeated in the rainbow blocks too** — the same standing note `tailwind-theme.css` already carries for its `@theme` mapping, now true of plain CSS as well.
- **Under Tailwind, `text-accentInk` is the utility**, mapped in `tailwind-theme.css` beside `text-accent` and repeated under the rainbow selectors for the reason above. The rule of thumb that decides which one a place wants, without thinking: if the colour lands on `background`, it is `--accent`; if it lands on `color`, `fill` or `stroke` against the page, it is `--accent-ink`.

## 1.4.0 — 2026-08-29

### ✨ Added

- **"The tooltip and info bubble" now says EVERY explanatory text is a bubble — not "usually", not "when it's long".** A short grey sentence under a field is the same debt as a long one and easier to talk yourself into: read once, by one person, on the day it was written, then costing that vertical space forever. If a control needs explaining, the explanation hangs off its "(i)"; if it doesn't, the sentence goes. Reported live and without qualification after an adopting app's browser-extension options page shipped four separate grey sub-captions, each individually defensible and collectively a wall of prose above the controls anyone came for. Names the excuse explicitly: **a surface with no component framework is not an exemption** — that page was hand-written HTML with a stylesheet, which is precisely the reasoning that produced the sub-captions.
- **Rainbow: the position belongs on the CONTAINER, not on the one visible element inside it.** The existing "wiring one set is not the same as wiring the mode" trap says to walk every equal-member set, which is right and is also the version that keeps failing, because "every set" is a list somebody maintains against a growing page. `.glim-hue` rebinds `--accent` for its whole subtree, so a position on a card hands its title badge, switch tracks, buttons and focus ring the same colour with nothing enumerated. An adopting app put the position on the section badge and shipped a mode that coloured eight badges and nothing else — buttons, switches and two whole secondary windows kept the single accent. Moving the call one element outward fixed all of it at once. Nested sets still start their own run at 0 and override the container for their own subtree. Carries the verification rule that would have caught it: measure something that is **not** the element you wired.
- **`openColorPickerPopover()` takes an optional `onClose` callback**, and the reason is a trap worth naming: while the popover is open, the row that owns its trigger must not be re-rendered, because replacing the trigger element strands the popover's own outside-click handler on a node no longer in the page — after which a second click on the new trigger neither closes nor re-opens anything. A caller that redraws its row on a colour change therefore applies the colour live in `onChange` and does the redraw in `onClose`, once. Found building an adopting app's options page, where a reset badge that only appears once the colour has moved, and a diagnostic report naming the current accent, both depend on that redraw. `close()` is now idempotent too, so the callback fires exactly once however the popover was dismissed.
- **"The user-owned axes" now rules out an "Automatic" entry in the language list.** The app resolves the browser/OS locale, maps it onto the nearest locale it has, and preselects that real language with its flag — an "Automatic" / "System" / "Follow browser" option looks like a choice and is an excuse, because it does not answer the question somebody opens the list to ask, and it makes the closed field read "Automatic" while the UI is plainly in German. Reported without qualification on an adopting app's extension options page. The fix is smaller than the entry it removes: the resolution already had to happen to render the first screen, so the only change is showing its result. Carries a corollary for the custom listbox the same section already allows — once a surface builds one, its options may use a real flag sprite instead of the emoji prefix, since the emoji rule exists only because a native `<option>` can hold nothing else.
- **"Switches" now rules out the native checkbox outright.** `<input type="checkbox">` renders the operating system's box, which follows none of the engines — shape, colour, motion — and sits in a GlimStone surface looking pasted in from another program. Same origin, same page, same flat report. Records the excuse that produces it ("this page has no component framework") and why it does not hold: the switch is markup plus CSS and belongs in that surface's own stylesheet. Also names `accent-color` as a non-fix, since it recolours one part of a control whose geometry, knob and transition still ignore everything else here.

## 1.3.0 — 2026-08-26

### ✨ Added

- **"The one horizontal selector" now documents the well at a SECOND, compact scale — one variant with a sizing option, never a second variant.** A page-level picker that appears once (theme, shape, motion) and a picker that repeats a dozen times down the same page (every schedule card's mode picker, a notification-trigger row, a weekday strip) are the same control at two scales. The small one is the same well with the equal-width pinning switched off: segments hug their own content instead of pinning to a shared minimum width, height comes from padding plus line-height, the strip wraps, and the track is `width: fit-content` so it hugs its own segments rather than stretching to a block parent (which also retires the hand-rolled `inline-flex`/`align-self` wrappers the three big call sites carried). Same groove token, radius, idle/active fill, crossfade and keyboard/RTL/disabled behaviour either way.
- **The small selector shares the big one's fill logic, and the rule that forces it: inside a selector, only the chosen segment is a badge.** BombVault first shipped the compact scale as a genuine third variant whose idle segments each kept their own visible fill, so the strip read as a groove holding keys. Reversed live (*"Die kleinen Selektoren sollen so aussehen wie die grossen! Die nicht ausgewählten Optionen sollen kein Badge sein"*): an individually filled idle segment is exactly the per-segment badge an unselected option must not be, and the existing "every tab is a badge, not just the selected one" rule governs the BARE-badge default, whose segments have no enclosure of their own — it does not survive being carried into the well. A user reads the two scales as one control family, so a fill divergence between them gets reported as a bug, not read as a variant's character. Records the collapse itself as the general lesson: two variants whose only remaining difference is a prop that already exists are two chances to drift apart, so reach for a sizing option on the one variant before reaching for a second variant.
- **New trap: a compact selector's groove must contrast against BOTH surfaces it can legally sit on, not just the one it was drawn against.** A page-level picker has one parent to be distinct from; a picker that repeats per card sits directly on a Card's surface in one place and inside a nested well one step deeper in another. Reported live as *"Ich sehe nirgends die neuen horizontalen Selektoren"* — six of nine call sites were wrapped in a well painted the very token the strip had picked for its own groove, so groove and parent computed to the identical `rgb(232,232,232)` and no enclosure existed on screen. **A zero-delta enclosure is not an enclosure**, and the defect is invisible to any class-presence check: every class name was correct, the component rendered what it was asked for, and the bug exists only as two numbers being equal — it surfaces only when someone measures the two computed backgrounds or looks at it. Documents fixing it at the variant rather than per call site, testing the invariant (groove ≠ parent, groove ≠ idle segment) rather than the value, unifying the big instance onto the same deeper token (which measured as the *stronger* enclosure there too, 1.94:1/1.53:1 against 1.31:1/1.21:1), and the idle-label contrast this costs (4.57:1 dark / 5.12:1 light — AA cleared by 0.08 in dark, so a further deepening needs a text-token change in the same commit).
- **New Badges rule: a square icon badge takes ONE size across the whole app, not one size per role.** The existing "look up the role's existing token" bullet fixes drift within a role; this is what happens once every role is internally consistent and the result is still wrong. An adopting app ran a proper role-based audit — standalone corner pair, badge beside a field, badge in a dense row — measured each role correctly, shipped three stages, and still failed, because all three roles appear at once inside a single expanded card (28/28/32/32/24/24 px side by side, reported twice). **"Internally consistent per role" is not a property a user can perceive**: a user sees one card, roles are an authoring-side abstraction, and a "these may differ because they play different roles" justification is itself evidence the split is wrong. Documents picking the single value by which number changes the fewest pixels and breaks no working alignment, plus a regression test and a written record that the split was tried and rejected, since the per-call-site reasoning behind it is genuinely persuasive and comes back otherwise.
- **The corollary: a dense row absorbs the one badge size by adjusting its own row padding, never by shrinking the badge.** A snapshot row at `py-2.5` around a 24px badge and the same row at `py-1.5` around the 32px badge are both 44px rows — a bigger badge in a list of unchanged density, rather than a list that grew. Anything sized to match a badge without being one (a colour swatch) follows the badge, not the reverse, and a genuinely taller field keeps its own height while the badge centres against it.
- **New Badges rule: a delete badge is not styled differently from the badges beside it** — no red tint, no red hover, and no grey-neutral exemption either. It takes the same hue and treatment as every other badge in its card, with its meaning carried by its glyph, its hover tooltip and the confirmation it opens. Reconciles this explicitly with "Destructive and confirmable actions": that section's fault-colour rule governs the control that actually ends something (the commit button inside the confirmation window, still status-red), not the trigger that opens it. Also names the grey-neutral version as the same mistake in the opposite colour and the easier one to ship by accident — `neutral` is usually a tone exempted from rainbow positions, so a "quiet" delete badge takes no colour-engine position at all and stays grey in every palette while its siblings follow the hue, a rule 9 violation that reads as restraint. Matches the same call already shipped for "Disable"/"Deaktivieren" buttons.
- **The user-owned axes: the language catalogue holds at scale.** BombVault was brought from 26 to 42 locales for cross-app parity with KnightLoader, in one sitting by one writer rather than a batch split across parallel agents, with verification hard-checked by a key-parity test plus a per-key raw grep (exactly one match per file — zero means missing, two-plus means a duplicate a test alone may not catch).
- **New Badges rule: a heading badge can be SPLIT into a leading ordinal cell and the card's own name — one pill, two visibly distinct parts — and it earns that only on a page whose cards are a genuine ordered sequence.** Built for BombVault's Recovery tab, where the cards are the numbered steps somebody actually walks in order, so the number is true about the card and would still be true with the badge deleted. Six independent settings cards have no such ordinal, and numbering them would invent a sequence the page doesn't have — the same test the colour engine's own "a badge with no persisted state at all doesn't own a rainbow position" already applies to hue, one register over: a structural signal handed to something with nothing behind it manufactures information rather than carrying it. Explicitly not a general-purpose "put a number on things" device.
- **ONE badge with an internal seam, never a number chip parked beside a heading badge.** The number names *which* step the card is exactly as the title names *what* it is, so it belongs in the same pill. The two-element version was what shipped first and failed in all three predictable ways at once: a 24px circle in the heading row never joined the colour engine (grey in every palette while its own card's notch took a rainbow position), was a second thing to position against rule 20's half-overlap notch, and once that notch went `position: absolute` and left the row it no longer even shared a baseline with the badge it was numbering. Records this as "two variants whose only remaining difference is a prop that already exists are two chances to drift apart" — the selector section's own lesson — at the level of a single control.
- **The mechanics, and the contrast requirement stated as an invariant rather than a value.** The shaded half is the badge's own two colours swapped, not a third colour: the fill mixes the accent 35% toward `--accent-contrast` and the ink flips to the other end of that binary via a new companion token (`--accent-contrast-inv`, with a rainbow-position counterpart rebound in every `.glim-hue` block including reactive mode's resting state); the seam is a logical `border-inline-end` in the label half's ink at 45% so it stays *between* the cells under RTL; the leading cell declares no radius of its own and the pill carries `overflow-hidden`, which is what makes the split correct in all three shape-engine modes without naming any of them. The notch's half-overlap position, hue participation, the `insetStart` override, wrapping and an info bubble in the label are all unchanged. **The two halves must stay distinguishable against EVERY hue in the palette and in both themes** — a seam that reads against one accent colour is not evidence it reads against the other seven. Documents the trap that forced the flip (shading toward the fill's own ink spends contrast that was never in surplus: a 20% mix drops `#1D99F3` from 5.95:1 to 4.23:1, and a custom accent on the contrast function's crossover fails on the first percent) and the live `getComputedStyle` evidence from the deployed build: worst prefix-ink 7.45:1 and worst half-to-half separation 3.38:1 across all eight positions in both themes, plus the ends of the colour space no palette contains (pure white 5.61:1, near-black 8.11:1, crossover grey 11.62:1), reactive resting 10.53:1/9.48:1, and the seam at 1.34–1.56:1 / 2.27–2.69:1 against the two halves. Carries the caveat that the first version of that table was computed from the formula rather than read off the page, and two of its eight figures were wrong.
- **REVERSED one round later: a heading ordinal is its OWN badge beside the name badge, not a shaded cell inside a split pill.** Supersedes the three split-badge entries directly above, which stay in place as the record of what was actually built. jdp, live review of the adopting app's Recovery tab: *"Die Cardtitelbadges mit Nummer sollen zwei getrennte Badges sein. Der Badge der Nummer nicht abgedunkelt."* Two visually separate badges of the same tone, size stage, fill and rainbow position — no seam, no shading, no tint. The content test is untouched (a number still earns its place only where the cards are a genuine ordered sequence), and so is the diagnosis of why the original grey chip failed; what changed is that the answer is two first-class badges instead of one merged box, since every failure of that chip was a property of the chip rather than of two-ness. Positioning moves up a level rather than being split between two absolutely-positioned boxes: the badge gains a flag for the notch's LOOK without its own placement classes, and the caller's `<h2>` becomes the positioned element, so `translateY(-50%)` resolves against the group's real height and a wrapped title still straddles the card edge correctly with no pixel offset anywhere. **The `--accent-contrast-inv` / rainbow inverse-ink token pair documented alongside the split is REMOVED, not deprecated** — the shaded cell was its only consumer — while the "shading a fill toward its own ink has no safe amount" finding is kept as the record of a direction, with the adopting app asserting the token's absence in its own test so it cannot come back silently.
- **Rainbow: a heading notch that owns its own position needs a widened hover target to reach rule 9's reactive reveal.** Rule 20's notch straddles its card's top edge, so the default `.glim-hue` hover/focus target is a thin overlapping strip nobody aims at reliably. The reveal target widens to the notch's own card — hovering or focusing anywhere inside it re-colours the badge — composing with rule 9 rather than replacing it, and scoped by a second marker class that travels only alongside the notch so proximity alone never lights up some other hued element inside the same box.

- **New section: "Two pages that do the same job."** Two list pages managing two kinds of thing are one page rendered twice, and every structural decision has to be made once for both. The drift this catches is invisible to a per-page review — each page is internally coherent every time you look at it, and only somebody switching tabs sees it. Found live in an adopting app whose two structurally-twinned pages had independently grown four disagreements (a feature card above the filter on one and below it on the other, sort inside the popover on one and beside the trigger on the other, three shared controls in three different slots, and one page hand-rolling an expander the other imported). Documents resolving a disagreement by picking one arrangement and MOVING the other page rather than averaging them (with the reason stated: list-operating controls stay adjacent to the list, standalone feature cards go above), that a shared component in a shared slot is what makes the sameness survive, that the two differ only where the domain does, and that the audit is a diff of the two render trees rather than a read of each page.
- **The horizontal selector's scale is chosen by the space the control gets, not by how often it repeats.** A filter menu breaks the existing repetition test: it appears once per page, so the test says use the big pinned scale, but it lives inside a popover a few hundred pixels wide where three segments against the app-wide 200px floor is 600px of content in a 260-420px panel — every option wraps and the control stops being horizontal at all. Repetition was only ever a proxy for available space; where they disagree, space wins, because the app-wide floor exists to make selectors in ordinary page flow match each other and a control in a fixed-width panel was never in that population.
- **New Badges rule: a two-option icon-only pair shows BOTH options, never one badge that cycles.** A single badge showing the current choice asks the user to infer the alternative from a glyph that is not on screen — acceptable for a preference, not for anything with a consequence (the case here decides whether a VM is shut down). Both segments render with only the active one filled. Adds the two constraints that make the pair legible: the glyphs must differ by SILHOUETTE rather than by colour, since an icon-only badge spends its colour on the badge background and the glyph is then the only thing left distinguishing the two at 16px (one round shape against one angular shape, never two members of the same family), and the pair still carries a label — two icons and nothing else is the unlabelled control this document already rules out.
- **New Failure-feedback rule: a failure message's FALLBACK is UI copy, and it is the copy most likely to ship untranslated.** A localisation pass finds labels, headings, hints and button text; it does not find `res.error ?? "Delete failed"`, because a fallback is not copy in anyone's mental model — it is reached only when the server had nothing to say, which is rare in development and common in exactly the failures users report. An audit of one app that had shipped 42 languages for months found 56 such literals across seven files. Documents translating the fallback with the same discipline as the label, keeping the domain in the message where the domain is the useful part, and guarding it with a PARSER rather than a grep: a codebase that documents its history in comments quotes these very strings, so a text scanner flags prose and a mechanical sweep mangles it, while a three-position AST rule found six further defects the hand-written sweep had missed entirely.
- **New Rainbow trap: moving a block of markup is a colour change, and nothing in the code says so.** Once heading positions come from a `nextHue()` counter incremented in render order, the counter's meaning is carried entirely by the physical order of the JSX — which makes cut-and-paste, the one edit everybody treats as cosmetic, a silent recolouring of everything below the cut. Gives the mechanical check (does the moved block consume a position, does the block it jumps consume one, does the move change either one's position relative to the counter's other consumers — jumping a hued card over a toolbar that consumes nothing is free, and moving two hued cards TOGETHER is free again) and requires the answer to be written at the call site in the same commit, so nobody generalises "moving cards is fine" out of a case that happened not to bite.

## 1.2.0 — 2026-08-23

### ✨ Added

- **New section: The time picker.** A floating popover replaces native `input type="time"` — two scrollable listbox columns (hours, minutes), no typing. Reuses the tooltip engine's own positioning contract rather than a fourth clamp implementation. First built for BombVault; documents two real live-caught dismissal bugs as hazards for the next adopter (a naive capture-phase scroll listener closing the popover on its own internal listbox scroll, and focusing an option before the popover's real position had committed triggering a browser auto-scroll that tripped the same listener).
- **"Saving" now states auto-save is the standing pattern, a manual button the exception.** The optimistic-update + immediate-PATCH + revert-with-`glim-shake` (discrete controls) / debounced-no-revert (continuous text) shape had proven itself across four different BombVault Settings cards over several rounds without ever being written down as a rule. Also names the two originally-documented cases where a manual Save button stays legitimate: a genuinely atomic multi-field submission, or a control that triggers an operation rather than persists a preference — extended below by two more.
- **Two more exception shapes that earn a manual Save button**, found on a full-page auto-save sweep: a one-shot write-only "apply this blob" action with no live current value to sync (a wholesale-replace config an unrelated scheduled process reads), and a field whose validity depends on agreeing with a sibling field before the write is even safe (a password-plus-confirm pair). Sharpens the multi-field exception with its actual behavioral tell — does Close genuinely discard the draft, or just hide it — via a worked near-miss that looked like the shape but failed that test and converts to auto-save instead.
- **"Failure feedback" now covers every failable action, not just settings auto-save.** A plain "Verify"/"Delete"/"Save"/"Check now"/"Poll" button with no optimistic value to revert still owes the same two channels on failure: a toast carries the message (never a permanent inline sentence), and the button plays `glim-shake` once. Found and fixed live on BombVault's Integrity tab, where a row of plain action buttons left the raw backend error sitting on the page as permanent text with neither the toast system nor `glim-shake` wired up. Documents four traps found rolling the fix out app-wide: keep a genuine persistent status verdict distinct from a failed-click message, one shake nonce per button (never shared across a button pair), a two-click confirm control must not un-confirm itself on the failure it's reporting, and an onBlur-submit control is a real exception to the key-remount shake mechanism (unmounting a focused element fires blur, which can loop).
- **The one horizontal selector needs one shared minimum width, not just per-strip equal-width sizing.** Per-strip equal-width alone still lets every selector instance in an app converge on its own different widest-label number, so a settings tab strip, a theme picker and a shape picker each read as a differently-sized control. Documents folding a single app-wide `MIN_WIDTH` floor into the same per-segment measurement (`Math.max`, never a cap) — calibrated against BombVault's own live numbers (174px/97px/62px converging on one shared 200px floor) as the worked reference.
- **New rule 20: stacked cards keep one shared vertical rhythm, `gap-10` (40px), including the gap below the tab strip.** A smaller `gap-6`/24px reads as cramped once every card carries its own notch title badge overlapping its top edge. The tab-strip-to-first-card gap reuses the same value rather than a bigger number invented just for that seam. First measured live in BombVault's Settings page.
- **New section: Icon glyphs.** Every icon glyph is a filled solid shape, never a stroked outline — a closed silhouette flips directly (`stroke="none" fill="currentColor"`, same path data), a line glyph (arrow, checkmark, plus, X) needs real filled geometry instead of a thicker stroke, and a structural detail that has to stay thin (a lock's shackle, a slider's track) renders as a thin filled shape rather than a stroke. The info-bubble `(i)` trigger stays the one deliberate exception. First formalized after KnightLoader's own icon set turned out to be a stroke/fill mix with no consistent rule behind it.
- **The menu/hamburger glyph is always exactly three horizontal filled bars** — never a sliders/equalizer icon standing in for it, which reads as a different control (adjust a value, not open a menu) to anyone who has seen either convention before.
- **New section: The tab-strip colour rule.** A tab (a horizontal-selector segment or a sidebar destination) carries colour in exactly one place at a time depending on interaction state: idle is colourless, hovering an unselected tab tints its icon (its own rainbow position, or the flat accent where the control has none), and selecting it fills the badge instead while the icon reverts to plain contrast ink. A genuinely different axis from rule 9's colour MODES (normal/rainbow vs. reactive-rest vs. reactive-hover) — this rule routes the same fixed colour to two different visual roles (icon, then badge) as one tab moves through idle → hover → selected, which rule 9's own always-same-target mechanism never had to do. Composes with rule 9's existing `--accent` cascade rather than adding a new one: the fix was moving an icon-tint rule from "unconditional at rest" to hover/focus-only and dropping its rainbow-mode gate, not new state. First implemented in BombVault's Settings tab strip and sidebar nav.

### 🐛 Fixed

- **"The tab-strip colour rule" now states the idle-colourless/hover-tints-icon reveal is specific to Reactive mode**, not universal. BombVault's first implementation tied the icon's colour to `:hover`/`:focus-within` unconditionally, which left idle tabs colourless in Normal and Rainbow mode too — only Reactive mode was ever meant to rest neutral and reveal on hover. Corrects the rule and the sidebar's own cross-reference to state the mode gate explicitly.
- **"Switches" no longer endorses hiding a row's own label because a heading above already states it.** The old "no second label" bullet actively invited exactly the shortcut that cost BombVault three separate build-then-reverse cycles (a Rainbow master toggle, a Restore-checks toggle, a weekly-digest toggle) plus a fourth batch caught only by a full-app audit. Replaced with the corrected rule: a switch always shows its own label; `hideLabel` stays legitimate only for a caller that draws the identical text itself in its own layout, never for "a heading further up the page covers it."
- **"The one horizontal selector" now states explicitly that the strip is sized to its own content, never stretched to fill its container** — a horizontal selector's row is a flex container that silently expands to an ancestor's full width the moment nothing opts out (a bare flex child of a column with the default `align-items: stretch`, or a block-level flex row in ordinary flow), which was never previously called out as something to guard against. Documented fix: `display: inline-flex` + `align-self: flex-start` on a wrapper, not a guessed pixel cap — `inline-flex` alone doesn't survive a flex/grid parent, which always blockifies a child regardless of its own declared display. Also documents a related trap in "a second styling: the well" — a well track's equal-width segments built from plain `flex: 1` shares (`flex-basis: 0%`) can silently truncate the widest label once an ancestor stops stretching the strip, because a flex item with a definite (including zero) flex-basis contributes that value, not its own content width, to a shrink-to-fit ancestor's intrinsic-size calculation; the fix is the same real-DOM-measurement-then-pinned-pixel-width mechanism an equal-width bare-badge strip already needs. Found live in BombVault: two Selectors (a light/dark theme picker, a round/soft/square shape picker) both stretched edge-to-edge across their own card, and fixing that with the wrapper above then truncated the well track's own longer labels until the measurement fix landed too.
- **"The one horizontal selector": unselected tabs are badges too, not bare text.** The existing "the tabs sit on the page as badges" line was read (correctly, by the letter of the earlier draft) as "bare until selected, `bg-carbon-hover` only on actual hover" — which read as unfinished on a settings strip with a dozen mostly-plain-text tabs. Corrected: every tab carries its own quiet fill (`bg-carbon-surface2`) at rest, and every tab in a set is the same width (sized to the longest label), not content-sized.

### 🐛 Fixed

- **The tooltip and info bubble** now states explicitly that a bubble must never be partially clipped by the viewport — not implied by the clamp/flip mechanism already documented, but a stated requirement. Found live: BombVault's own `InfoBubble`/`SelectorTab` — the exact component v1.1.0's own "Cross-app info-bubble standardisation" entries below call the anointed reference implementation — had in fact never implemented the clamp or the flip at all. Both positioned the bubble by centring it on the trigger and always opening downward, with zero viewport awareness; the gap had simply never been exercised by a trigger near enough to an edge until the "Wiederherstellungskit" (Recovery kit) info bubble in Settings overflowed the browser window and part of its text couldn't be read. Fixed by porting `reference/tooltip.ts`'s own `show()` math into a shared, pure, unit-tested function both call sites now invoke from a `useLayoutEffect`, measuring the bubble's real rendered size before it paints. Also found and fixed in the same pass: `.glim-bubble`'s documented `width: max-content` was missing from BombVault's own shipped CSS despite this file's prior "verbatim" claim — without it, a `position: fixed` box with only `left` set sizes itself via CSS shrink-to-fit (available width = containing-block width minus `left`), so computing a clamped `left` from a measured size and then applying it could change the box's own width and, via rewrapping, height — invalidating the very measurement the position was based on. Confirmed live at a narrow viewport: a bubble shrank from 280px to ~155px wide and grew from ~126px to ~253px tall after being positioned, fitting only by chance in that case. See "The tooltip and info bubble" for the corrected rule text.

## 1.1.0 — 2026-08-22

### ✨ Added

- A fifth motion-engine keyframe, `glim-shake` (`docs/design-language.md`, "The motion engine"; `reference/tokens.css`): a control refusing an action shakes instead of just silently reverting. A toggle switched on then rejected by a real backend precondition (no SSH configured for a feature that needs it, say) needs to visibly say "that didn't work," not just quietly snap back while the real explanation sits in a toast the eye may not be on yet. 360ms `ease-in-out` one-shot `translateX` oscillation, decaying `±4px → ±4px → ±2px → ±2px` through the middle four keyframes back to 0; under `prefers-reduced-motion: reduce` it swaps for a brief opacity pulse instead of nothing, matching every other entrance's reduced-motion substitution. Documented the one real implementation gotcha up front rather than letting it get rediscovered per adopting app: replaying the shake on a repeated identical failure needs a fresh DOM node (key the shaking element on an incrementing per-instance failure counter), not a re-toggled class — an animation already at rest doesn't restart just because its class briefly leaves and returns within the same frame. Named for the gesture, not the first control it shipped on — reach for it anywhere an optimistic UI update has to be undone (a rejected toggle, a form field failing server-side validation after looking locally valid, a drag snapping back because the drop target refused it), not just toggles. First implemented in BombVault.
- **The switch knob follows the shape engine too** ("Switches"): round → circle, soft → lightly-rounded square, square → sharp corners, reading the same `--radius-pill` token the track already does instead of a hardcoded `rounded-full`. Lives in the one shared switch component, so every switch in an adopting app picks it up automatically. First implemented in BombVault, found missing after the track itself had already been shape-correct for a while — a knob this small is exactly the kind of element that's easy to leave circular "because it always has been."
- **A second horizontal-selector styling: the well** ("The one horizontal selector"). The existing default (no wrapping bar, bare badges on the page) is right for a strip of independent, equally-weighted destinations; a small, genuinely exclusive set (three shape options, an on/off/reactive triple) can instead sit inside one shared padded track (`--carbon-surface2` background, `0.2rem` padding/gap, `--radius-control` on the track, flush segments), with the active segment filled and a plain colour crossfade on change — no sliding pill. Documented as an opt-in `variant` on the same component, not a second implementation: same keyboard/RTL/disabled behaviour either way, only the paint differs. First built for BombVault's shape picker, adapted from a shared "segmented row" widget already used the same way in TrickWork.
- **New standing principle: a component is wired into both engines AS it's built, not audited in afterward** ("The user-owned axes"). Adopting the shape/colour tokens isn't automatic just because they exist in the reference file — and the gap is easy to miss because a hardcoded value and a token-correct one render identically at the DEFAULT setting, only diverging once someone actually switches shape or accent. Every real instance of this found in BombVault was a small, low-visibility control (a dismiss "×", a quick-fill button, an ad-hoc status chip) styled in isolation instead of matching its nearest sibling — not a whole new component copied from an old pre-GlimStone one. The rule that actually catches it: before hand-writing a radius or colour value, grep for how the same KIND of control is already styled elsewhere and copy the token; verify by actually toggling the setting, not by reading the class list.
- **The version footer** ("The version footer"): an app's build version + the GlimStone version it targets belongs as one quiet line fixed to the settings window's own corner, visible on every settings tab without per-tab wiring, rather than a card on a single tab or a line competing with the app name in the nav rail. First built for KnightLoader, after the single-tab-card version was found to only ever be seen by someone who happened to open that one tab.

## 1.0.0 — 2026-08-21

The first public release of the design language: the full rule set, the reference tokens, and the componentry it took to keep BombVault, KnightLoader, TrickWork and every app since consistent with each other.

### ✨ Added

- Initial repository. Extracted the design language out of KnightLoader, where it had lived as `docs/design-language.md` + `web/src/index.css` + `web/src/lib/appearance.ts` since 2026-08-06, and merged it with the more complete rule set that had since evolved in the vault-only style guide (rules 9 through 19: three-way colour modes, section badges, content-edge alignment, everything-clickable-is-a-badge, borderless form fields, the window contract, hover-survives-hover, no forced `display`, replace-not-persuade, shared-box grouping — none of which had made it back into the KnightLoader repo copy).
- [`docs/design-language.md`](docs/design-language.md) — the full spec, all nineteen rules, the palette, the name's etymology, componentry (info bubble, horizontal selector, switches, the reveal eye, foreign-host-UI plugins), the two user-owned axes, the rainbow colour-mode system and its three known traps, the token contract, and the adoption steps.
- [`reference/tokens.css`](reference/tokens.css) — framework-free reference tokens and utility classes.
- [`reference/tailwind-theme.css`](reference/tailwind-theme.css) — the optional Tailwind v4 `@theme` mapping layer, split out from the framework-free tokens so a non-Tailwind app can skip it entirely.
- [`reference/appearance.ts`](reference/appearance.ts) — the shape/accent/rainbow logic, genericised from KnightLoader's copy (cache key, code comments) so it drops into any adopting app unchanged.
- **The user-owned axes, expanded from two to four.** Theme (light/dark/system, default system) and language now get the same explicit governance as shape and accent: applied once at the app root, never by the page that edits them. The accent's default — Sunflower gold `#FCC419` on first install, before anyone touches the picker — is now stated in prose, not just implied by a table annotation.
- **Right-to-left languages**, promoted from a single aside on the horizontal selector to its own section: logical properties handle most of the mirroring for free, but technical content (paths, URLs, filenames, log lines) stays pinned `dir="ltr"` + `text-align: start` regardless of page direction, and directional icons mirror while symmetric ones don't.
- **Non-Latin scripts**: how the font stack's fallback actually works (per-glyph, not a fixed named list), plus two concrete fixes — CJK letter-spacing reset (the base tightening reads as crowding on full-width glyphs) and a note that `.glim-num`'s tabular-figure feature is a Latin-digit convention with no defined effect on other numeral systems.
- A banner (`.github/assets/`): a running-bond brick wall with one gold-lit block, drawn from a real hand-authored master SVG and recoloured programmatically — the name's own opening line, "a small light in dark masonry," drawn literally. The gold block is the constant core across both theme variants; only the stone tone swaps to keep reading against its background — the same pattern every other logo pair in this house style follows.
- **Named the two existing mechanisms and added a third.** Shape was already called "the shape engine" in passing; formalised that, and named the theme/accent/rainbow mechanism **the colour engine** (one mechanism, three inputs, all resolving to the same handful of tokens). Added **the motion engine** as its own section — it existed as CSS (four keyframes, a `prefers-reduced-motion` block, rule 10) but was never documented as a system with its own timing rationale.
- A short "engines we don't have" note explaining why browser-engine differences (Chromium/Gecko/WebKit) stay out of scope: everything GlimStone does runs through standard CSS media queries and custom properties, which behave identically across engines — engine-specific branching is an application concern, not a design-language one.
- **Repository made public**, with the license and funding files that implies: AGPL-3.0 (name and branding reserved, matching every other own-named product repo), `FUNDING.yml`, a License badge, and the Buy Me a Coffee button top and bottom.
- **Chosen mark: one lit block in a running-bond brick wall** — literal to this document's own opening line. An earlier placeholder (a synthesised 3x3 grid, drafted before a real hand-drawn logo existed, alongside two other concepts — a seal with a sunburst was the other finalist) was later replaced by the user's own real design.
- **Five new sections extracted from real, working code rather than invented:** Badges (four shape registers, named size stages with one canonical source, the pixel-parity-across-element-types discipline, the `font-size: 0` + `vertical-align: middle` trap — generalised from CannonadeCommand's production badge system, previously only in its app-specific subnote), Toasts (duration, stacking, hover-pauses-and-preserves-remaining-time, severity-filtered quiet mode, toast-vs-dedicated-surface judgement — from KnightLoader's `lib/toast.tsx`), Empty states (the shared `EmptyState` shape, and the zero-items-vs-zero-matches copy distinction), Destructive and confirmable actions (reversible fires immediately, irreversible gets a real modal stating exact stakes, the control is always the fault colour), and Charts, marked provisional since only one example (a speed graph) currently exists.
- A short technique note in `reference/tokens.css`: cap a pill radius against the element's own height (`min(var(--radius-pill), 50%)`) rather than applying the raw token, so a compact badge doesn't over-round into a lozenge. (Later found to be backwards — see Fixed, below.)
- **The type scale**, extracted now that the underlying app is actually consistent: four repeatable steps (20px heading, 14px body, 12px dense, 11px caption — the last covering three treatments of one size, not three sizes), plus an explicit note that a page's one hero figure and any brand-wordmark instance are deliberately *not* part of the scale. Not named an engine: unlike shape/colour/motion, nothing varies it — it's a fixed reference table, the same category as the palette.
- `--text-heading`/`--text-body`/`--text-dense`/`--text-caption` tokens in `reference/tokens.css`; `.glim-eyebrow` and `.glim-bubble` now read `var(--text-caption)` instead of their old separate 10px/11.5px literals.
- Rule 14 gains a scroll-to-cycle behaviour for `<select>` elements: a new [`reference/selectScroll.ts`](reference/selectScroll.ts) (`enableSelectScroll()` / `enableSelectScrollForAll()`) lets a closed dropdown answer the mouse wheel directly, stepping `selectedIndex` and firing a real `change` event without ever opening the native dropdown. The platform default only wires the wheel up once a `<select>` is already open; this closes that gap for values people reach for constantly (a font, a preset, a language) so they don't cost a click first. Framework-free, idempotent, dependency-free like `appearance.ts`. Requested while building a character-set/font-heavy settings surface in an adopting app, where scrolling through options one at a time is the natural gesture.
- A new "The sidebar" section documents the persistent left-rail navigation already live in BombVault and KnightLoader (brand mark top, vertical icon+label destination list, Settings pinned at the bottom below a spacer, `--carbon-sidebar` as its own surface token, real `aria-current="page"` navigation semantics rather than the ARIA tabs pattern the horizontal selector uses) as GlimStone's own canonical multi-destination pattern for the first time — it existed in two apps' code but nowhere in the design language itself. Also documents the sanctioned lightweight alternative for a genuinely simple, single-workspace app: a small square Settings badge (gear glyph, top-right, `--radius-control` not the pill) instead of a full rail, opening Settings as its own full-page view with no preview or working cards behind it.
- New rule: version numbers belong in Settings, never in a persistent footer — a version string in permanent page chrome is read once and then costs a line forever, the same objection rule 8 already makes about explanatory prose sitting under every control.
- The Language axis (under "The user-owned axes") now documents flag-emoji-prefixed options for the language `<select>` — a new [`reference/flagEmoji.ts`](reference/flagEmoji.ts) (`flagEmoji(isoCode)`) converts an ISO 3166-1 alpha-2 code to its regional-indicator flag emoji by string concatenation alone, so a native `<option>` (which can only ever hold plain text, never an image or CSS background) can still show a flag next to each language name without forcing a custom-built dropdown just to render one. Notes that a component-framework app that already isn't using a native select for other reasons may reasonably build a custom dropdown with a real flag-icon sprite library instead — this is the plain-`<select>`-compatible default, not a mandate to avoid a fancier approach elsewhere.
- New [`reference/colorPicker.ts`](reference/colorPicker.ts) is a saturation/value square + hue bar — real DOM the app owns, extracted from CannonadeCommand's own `inlinePicker()`. `.glim-picker`/`.glim-picker-sv`/`.glim-picker-hue` in `reference/tokens.css` give it the shared look. `openColorPickerPopover(trigger, hex, onChange)` wraps it in a floating `.glim-picker-popover` anchored to a trigger element (closes on outside click, Escape, scroll or resize) — the recommended default for a compact settings card, where embedding the picker permanently grows the card every time one is added. The bare `colorPicker()` (no popover) is still there for a page with genuinely dedicated, permanent space for exactly one control. The popover also carries a paired `.glim-picker-hex` text field (CannonadeCommand's own `cc-set-hexin`) — bidirectionally synced, so a value can be typed or read back exactly, not only dragged.
- New `.glim-tint-hover` on the colour engine: the same rest-quiet/hover-reveals wash `reactive` mode already gave the whole app, now available per-element regardless of the user's own on/reactive setting — for a row of equal-weight ACTIONS (not a persistent selection), permanently washing every member under plain `on` competes with the page instead of accenting it. Its own reveal now reads the stronger `--item-hue-badge` tier (50%), not the list-row `--item-hue-wash` (16%) — a hover reveal is a deliberate, momentary state closer to a badge's own "clearly coloured" bar than a list's "don't overwhelm a column of these" one.
- New `.glim-tint-badge` on the colour engine, alongside a new `--item-hue-badge` tier (50% alpha) in `hueVars()`: for a compact circular badge that needs colour AT REST because it has no checked/active state of its own to fall back on.
- The Language axis's custom-listbox escape hatch (design-language.md, "The user-owned axes" > Language) now documents a follow-up fix for the Windows flag-rendering gap it already accepted as expected: an app that upgraded to a custom listbox (real page DOM, not a native `<select>`) can layer in [`noto-color-emoji-flags`](https://www.npmjs.com/package/noto-color-emoji-flags) (OFL-1.1, a ~800KB COLR-vector subset of Noto Color Emoji containing only flag glyphs) scoped to just the flag span, so Windows shows real pictorial flags too instead of the two-letter fallback tag. Deliberately not Twemoji's own country-flags subset — Twemoji is CC-BY 4.0, which fails the OFL-only asset rule. `reference/flagEmoji.ts`'s own comment updated to point here; the function's output itself (plain regional-indicator codepoints) is unchanged — this is a presentation-layer fix, not a behavioural one. First adopted in TrickWork.

### 🐛 Fixed

- `reference/tokens.css` was missing the base `body` rule (background, font stack, letter-spacing) and `* { box-sizing: border-box; }` entirely — dropped during the original extraction from KnightLoader's `index.css`. An app following the adoption steps literally would have gotten every component class but not the page-level defaults they assume.
- Generalised the few remaining named references to specific sibling apps (README opener, the info-bubble and horizontal-selector sections) — this document was already meant to be app-agnostic; the wording hadn't fully caught up.
- `.glim-live`'s pulse had no `prefers-reduced-motion` fallback at all — an infinite 2s animation is exactly the category that preference exists for, unlike the one-shot entrances that already degraded correctly. It now renders as a static, fully-opaque dot under reduced motion instead of continuing to pulse.
- [`reference/appearance.ts`](reference/appearance.ts) failed to typecheck under a consumer's stricter TypeScript settings (`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`) — found while adopting GlimStone into a new strict-mode project. `rainbowAt()` now throws a descriptive error on the (practically unreachable, since `usablePalette()` never lets the palette go empty) case its indexed lookup can't statically prove is defined; `cacheAppearance()` now builds its cached payload with a conditional spread so an absent `rainbow` argument omits the key entirely instead of setting it to `undefined`. Both fixes preserve the exact same runtime behaviour — this is a type-only correctness fix for adopting apps that run with these stricter flags, not a behaviour change.
- [`reference/tokens.css`](reference/tokens.css) never actually implemented the documented "theme defaults to system" behaviour — `docs/design-language.md` states that an unset `data-theme` "follows the OS via `prefers-color-scheme`", but the stylesheet had no `@media (prefers-color-scheme: light)` block at all: the bare `:root` unconditionally applied the dark palette, so any adopting app that never explicitly sets `data-theme` opened dark regardless of the OS's light preference — the exact "opened dark on a light-mode OS nobody asked for" mistake the design language itself warns against. Added the missing media-query tier (`:root:not([data-theme="dark"])` under `@media (prefers-color-scheme: light)`, mirroring the same token values as `[data-theme="light"]`), so an unset theme now genuinely follows the OS in both directions, and an explicit `data-theme="light"`/`"dark"` override still wins regardless of OS preference. Found while wiring a full appearance-settings panel (shape/accent/theme pickers) into a new adopting app.
- The flag-emoji rule overclaimed "renders as a real flag glyph on every modern OS" — verified on Windows and that's wrong: Windows renders the same regional-indicator codepoints as a compact two-letter tag instead of a pictorial flag, a deliberate long-standing Microsoft emoji-font policy, not a rendering bug. macOS, Linux, iOS and Android do show the actual flag. Corrected the claim in both `docs/design-language.md` and `reference/flagEmoji.ts`'s own comment — the mechanism and the recommendation are unchanged, only the "every OS" wording was inaccurate.
- The rainbow mode's active-row highlight silently collapsed to the same flat wash as every other row, in both `on` and `reactive` mode, because `.glim-tint`'s own box-shadow declaration has higher CSS specificity than a typical single-class `.active`-style app rule and always won the cascade — an adopting app's own "this one is selected" class needs to ALSO carry the shared `.glim-active` marker, not just its own app-specific equivalent, for `tokens.css`'s composition rule to engage at all. `[data-rainbow] .glim-tint.glim-active` now covers both `on` and `reactive` (the previous fix, in an earlier reactive-mode pass, only generalised to the mode it happened to be tested against). Found via a real adopting app (TrickWork) whose queue never carried `.glim-active` on its own active row.
- The wash opacity (7%) shipped in the first version drew three independent "the mode does nothing when I turn it on" reports from the same adopting app before anyone measured the actual rendered colour rather than eyeballing it — it was applying correctly the whole time, just under the threshold a person registers as change. Raised to 16% (the selected-row soft tint: 14% → 22%).
- `.glim-bubble` previously had its own bespoke, JS-free styling (no arrow, no viewport clamping, no flip) — visibly inconsistent against a sibling app's own tooltip system built on the real thing. It now IS the real thing: same engine, same look, matching CannonadeCommand's reference exactly.

That hands control to a browser/OS surface entirely outside the page — a genuinely separate top-level window on some setups, not an inline popover — directly contradicting a standing preference from CannonadeCommand's own build ("ich will das Farbwählfeld fest integriert") and unverifiable in automated testing besides. The picker section now documents ONE layout: every custom colour value (a single accent, or one of a palette's several positions) gets the same trigger — a flat swatch, same size as the presets beside it — that opens the shared popover pre-synced to its value.
- Rainbow's own docs never said the mode has to cover more than the first list it looked like an obvious fit for — an adopting app that wired only its download queue implemented "colours one list," not "rainbow mode," and kept drawing "it doesn't apply" reports no matter how many times that one queue's own mechanics were fixed. New fifth trap: `rainbowColor(i)`/`hueVars()` are already general-purpose: walk every genuine equal-member set in the app (segmented-control segments, icon toggles, anything that isn't the only one of its kind on the page) and wire each one.
- An icon-only badge that owns a rainbow position colours its own background (`.glim-hue` + `.glim-tint`/`.glim-tint-hover`), NOT its glyph — an earlier revision of this rule additionally recoloured the glyph via `.glim-hue-icon`, which read as one colour too many once a real adopting app tried it. `.glim-hue-icon` is still available, but only for a genuinely backgroundless glyph with nothing behind it to wash — not the default pairing for a real badge.
- A real TOGGLE badge (a genuine checked/unchecked state of its own) went through two rounds of idle-background washing (`.glim-tint`, then the stronger `.glim-tint-badge`) and a real adopting app rejected both: "die iconbadges sollen nicht eingefärbt sein und erst wenn man sie klickt. diese halb abgedunkelt eingefärbt sein gefällt mir nicht." The correct behaviour needed no new mechanism — `.glim-hue` alone (unconditional) plus the component's own checked-state fill (`background-color: var(--accent)`) already means nothing shows at rest and the position colour fills solid once checked. `.glim-tint-badge` is still real, just not the default for a toggle — reach for it on a badge with no checked state to fall back on. A badge with no persisted state at all (a momentary action — undo, redo, zoom) doesn't own a rainbow position, full stop: there's no "clicked and stays that way" moment for a fill to attach to, so wiring it in just means faking a rest colour again.
- The horizontal selector's own rainbow behaviour was never specified, so an adopting app washed every segment at rest the same way a list row does — noisy, since the selector's own fill already says which one is picked. Documented: only the SELECTED segment owns a position; inactive segments get neither `.glim-hue` nor `.glim-tint` at all.
- `border-radius: min(var(--radius-pill), 50%)` was documented as the fix for a compact badge over-rounding into a "pointed lozenge." It's the opposite: `50%` resolves per-AXIS (of width, of height) *before* the border-radius overflow algorithm runs, so on any non-square element it hard-codes two different corner radii up front and renders as a visible ellipse, not a pill — confirmed on a live 220×120 test box, an ellipse with the guard, a correct stadium without it. The raw token alone (`border-radius: var(--radius-pill)`) already renders correctly on ANY box, square or not — the browser's own corner-overflow algorithm scales all four corners down together to fit, with no capping needed. Docs and `reference/tokens.css` corrected; never write the `min(…, 50%)` guard, on badges or anywhere else.
- Cross-app info-bubble standardisation: BombVault's shipped `InfoBubble`/`.glim-bubble` is now the anointed reference implementation for the shared tooltip/info-bubble engine, and this repo's own copy had drifted from it in several real ways — one of them a genuine accessibility regression, not a style preference. `.glim-info-icon:focus-visible` set `outline: none`, actively removing the only visual signal a keyboard user had that the trigger was focused (opacity `.8 → 1` reads identically to plain hover, so it isn't a substitute). Split into its own rule with a real `outline: 2px solid var(--focus-ring); outline-offset: 2px` — the exact treatment every ordinary button and link already gets from this file's base `:focus-visible` rule — plus a new `border-radius: var(--radius-pill)` on the icon itself so that ring traces a circle around the glyph instead of a square. Documented in `docs/design-language.md` as the design language's one deliberate, sole exception to rule 5 ("hierarchy from type and colour, never borders"), stated in both rule 5 and the tooltip section, cross-referencing each other rather than duplicating the reasoning: mouse/hover interaction never shows a border, only keyboard focus does.
- `reference/tokens.css`'s `.glim-bubble` had drifted from its own recipe on five separate properties, verified against BombVault's real, shipped CSS: `background-color` was the WELL tone (`--carbon-surface2`) instead of the one raised surface every other card-like element reads (`--carbon-surface`) — a floating bubble is a card, not a sunken well. `box-shadow` was a bespoke flat `0 8px 24px rgba(0,0,0,.55)` with no hairline, instead of this file's own `var(--elevation), var(--hairline)` pair — the same recipe `.glim-card`/`.glim-toast` already use — so the bubble was the one surface in the whole language missing its top-light hairline. `padding` was `9px 12px`, corrected to a tighter `7px 10px`. `font-size` was a hardcoded `12.5px` that directly contradicted this same file's own type-scale comment three lines above it (which already claimed the info bubble's text was one of the three treatments `--text-caption` covers) — it now actually reads `var(--text-caption)` (11px), so the comment stops lying about the rule beneath it. `white-space` was `pre-line` (preserves literal `\n`s), corrected to `normal` — every real tip is a single wrapped sentence, not a multi-line block. `border-radius` simplified from a `min(var(--radius-control), 10px)` guard to the plain token — the two have never actually differed under any of the three shipped shapes, so the guard was inert. `.glim-bubble::before`'s and `.glim-bubble--above::before`'s arrow `border-color` now match the corrected background so the arrow still reads as part of the same shape it points from.
- Resolved a standing internal contradiction spanning `docs/design-language.md`, `reference/tokens.css` and `reference/tooltip.ts`: the motion-engine section always said the info bubble gets a 110ms fade, while the tooltip section claimed the opposite ("no transition — an instant display toggle") and the shared engine's own bubble element never actually carried the `.glim-fade` class needed to animate at all — so in production it really was instant, for a different reason than either doc passage gave. `tooltip.ts`'s `bubbleEl()` now applies `glim-fade` to the shared bubble (a CSS animation replays automatically when an element re-enters rendering after `display: none`, so no other change was needed); the tooltip section's prose now agrees with the motion-engine section instead of contradicting it, and states that closing has no fade (asymmetric on purpose — a hover-driven aid should vanish the instant the hover ends).
- `wireTooltips()` had no Escape handler at all — the only way to dismiss an open bubble by keyboard was to blur the trigger, which also gives up your place on the page. Escape now hides the bubble without moving focus, matching BombVault's own `InfoBubble` component.
