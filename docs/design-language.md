# The design language

A layered, low-noise interface system: a small light in dark masonry.

**The palette is not ours to invent.** The ground, the surfaces, the text ramp and the state hues are IBM Carbon's neutral greys and support tones — the same values already used consistently across every app that shares this language. GlimStone briefly had a warm near-black of its own, and it read as brown beside everything else. A design language shared across apps has to share its ground first; what GlimStone contributes is the *system* — the rules below, the shape engine, the rainbow, the info bubble — not a second set of greys.

Accent presets in the picker are the same five across every app: Sunflower `#FCC419`, Blue `#1D99F3`, Green `#6FDC8C`, Red `#FF8389`, Purple `#BE95FF`. Someone who picks "Blue" in one app finds the same blue in the next.

The light accent is **the same hue, darkened** (`#8E6A00`), not a different colour: gold on white is unreadable at 11px, and Carbon's own answer to that is to darken the hue rather than switch it.

## The type scale

Not an engine, on purpose: an engine resolves a *variable* input (a setting, an OS signal) into tokens. Nobody sets their own type scale — this is a fixed reference table, the same category as the palette above, not a mechanism.

| Size | Role |
|---|---|
| 20px | Heading — a section or page title. |
| 14px | Body — the default for everything that isn't one of the other rows. |
| 12px | Dense — list rows, table cells, anywhere many instances stack and body size would crowd. |
| 11px | Caption — three treatments of the *same size*, not three sizes: a plain muted caption, `.glim-eyebrow`'s uppercase+letter-spaced label, and the info bubble's popover text. The treatment carries the distinction, not the size. |

**Two sizes exist and are deliberately *not* part of this scale**, so nobody extends them into steps that don't exist: a page's one hero figure (rule 2) is sized on its own merits case by case, not from a repeated "display" step — forcing every hero into one fixed size would fight the same rule that says there's exactly one hero and everything else is quiet. A wordmark or brand-name instance is typography for a specific, singular piece of chrome, not a heading size available for reuse elsewhere. Treat any large one-off number the same way: it's not a gap in the scale, it's a case the scale was never meant to cover.

**How this table got here:** three near-identical caption sizes (10px, 11px, 11.5px) drifted apart across an app's history before being consolidated to the single 11px row above — the same failure mode rule about badge sizing warns against, just for text instead of boxes. If a future audit finds a fourth size claiming to be a caption, that's the bug to fix, not a fourth row to add.

## The name

Middle English *glimme*, "shining brightness; radiance", attested around 1400 in *Pearl* — MS Cotton Nero A.x, the same manuscript that carries *Sir Gawain and the Green Knight*. The Gawain-poet himself alliterates the two halves together in line 172: *"euer glemered & glent al of grene stones."* The later thieves'-cant sense ("douse the glim", 1700) is a narrowing of a word that had already been English for three centuries. The German ear hears the same root in *glimmen* and *Glimmer* — the gold that sits in dark rock.

Considered and rejected, so nobody reinvents them: **GlimWard** (the 2016 fantasy series *Glimwarden* already uses exactly this word, exactly this sense), **GleedStone** (best etymology of the lot — Old English *glēd* = ember — but German final devoicing turns it into *Glied*, "limb"), **GlimSolar** (a castle's solar is its private chamber, but a German reader hears "solar panel"), **GlimHearth** (too close to Hearthstone), **GlimCloister** (Cloister is a typeface), **WickStone** (Wick reads as a cough remedy).

The CSS prefix is `glim-`.

## The rules that keep it calm

1. **One raised surface.** `.glim-card` is the only elevation. Never nest a card inside a card — group content with spacing and a section title instead.
2. **One hero per page.** Exactly one element carries weight. Everything else is supporting detail at small type.
3. **The accent marks activity, nothing else.** It is reserved for the active nav item, the single primary action, progress fills, and the brand mark. A page has at most one solid accent button. A control that is *always* on in every row is not activity — it has to be de-coloured.
4. **Four state hues.** accent = running · green = settled · red = fault · neutral = waiting. Paused shares the neutral tone; its label and its resume control carry the difference. Never introduce a fifth hue.
5. **Hierarchy from type and colour step, not from borders.** Separators are hairlines at low opacity; boxes are a last resort. **No vertical marks at all** — no rails, no leading-edge bars, no 3px accent stripes. What is selected is *filled* with the accent; what owns a rainbow position is *washed* with it. A rail also breaks under the square corner setting, where it stops reading as a mark and starts reading as a stray border. One narrow, deliberate exception exists — the info-bubble trigger's `:focus-visible` outline; see "The tooltip and info bubble" below for why.
6. **Secondary actions appear on hover.** A long list reads as content, not as a wall of buttons. The primary action for a row stays visible.
7. **Digits use `.glim-num`** (tabular + lining numerals) wherever they change or stack, so nothing jitters while counting.
8. **Explanations live in a bubble, not on the page.** A control that needs explaining carries a neutral `(i)` beside its label; the text appears on hover or focus. Prose printed under every control is read once and then costs vertical space forever, and a page of grey paragraphs hides the controls it was meant to clarify. If something cannot be explained in a bubble, the control is wrong, not the label.
9. **Colour modes are three-way, never two-way — and they apply to everything.** Every coloured element needs *three* states: normal/rainbow (mode colour) · reactive-rest (neutral grey) · reactive-hover (mode colour). This applies to **every** element on a page, not just the obvious ones: badges, buttons, links, fields, switches, icons. A page is only finished once **nothing** is left that ignores the mode — "half of it respects the mode" is a bug, not a state. Checking off "accent applied" and stopping there ships the wrong thing for anyone running reactive.
10. **Reactive is a colour rule, not a motion rule.** Animations keep running under it. Muting a pulsing indicator in reactive mode turns the feature off for the person who asked for it.
11. **Every heading is a filled section badge** — never bare text, never a full-width bar with no radius. A section badge is **always coloured**: it is a heading, not a control, so rule 9 does not apply to it.
12. **Headings align to the content edge, not the window edge.** Inside a foreign host UI, the reference edge is the **host's own main navigation**, not the column beneath it — the section badge lines up flush-left with the host's menu bar. That edge is **measured** (e.g. a `--align-left` custom property), never guessed as a fixed padding value, or it drifts with theme, font size, and fixed-vs-fluid width.
13. **Everything clickable is a badge — including links.** A plain blue text link between badges is a foreign object. **A small, single-purpose action badge (copy, reset, undo) carries an icon, not a text label** — "Copy" or "Reset" sitting in its own small pill reads as a stray caption next to the icon-only controls around it, and costs the row width a text label doesn't need to spend. Name carries as `title`/`aria-label`, never as visible text, the same way `iconToggleButton` already works. This doesn't apply to a primary action a page genuinely wants read as a sentence ("Export settings," "Import settings") — those keep their label; it's specifically the small secondary badges that sit beside other icon-only controls.
14. **Form fields are borderless and filled**, focus is a brightness step rather than a ring. Anyone setting `appearance: none` **has to supply the arrow** themselves. A native `<select>`'s open dropdown stays OS chrome — that's a compromise, and it gets named as one, not sold as "on brand." **A closed `<select>` also answers the mouse wheel**: scrolling while hovering steps `selectedIndex` up or down and fires `change`, without opening the native dropdown at all — the platform default only wires the wheel up once the list is already open, and a value someone reaches for constantly (a font, a preset, a language) shouldn't cost a click first. `reference/selectScroll.ts`.
15. **A window is a window**, no matter who renders it. Same surface, same radius, same elevation, title as a badge, button row at the bottom. **Opacity is off-limits**: `opacity` on a container composites the whole subtree, darkening happens through colour instead. For long content, the title and button row stay anchored — only the region between them scrolls.
16. **A control that only appears on hover has to survive hovering itself** — otherwise it vanishes at the exact moment someone reaches for it.
17. **Never override a foreign container with `display: … !important`.** The host shows and hides it on its own; forcing `display` leaves it stuck visible.
18. **A native control gets replaced, not persuaded.** Where the host UI renders a widget whose insides CSS can't reach (an open native `<select>`), there is exactly one right answer: swap in the app's own replacement, which it already has anyway. "Closed, it looks on-brand" is not an adoption, it's a half-finished rebuild, and it reads as one.
19. **Controls that belong together share one box.** Same height, same radius, same font, one row. Elements that live in different parents can never share a row — move the element itself, don't nudge the spacing to fake it.
20. **Stacked cards keep one shared vertical rhythm: `gap-10` (40px), including the gap below the tab strip.** A smaller gap (`gap-6`/24px) reads as cramped once every card carries its own notch title badge overlapping its top edge — badges that close together lose the "separate section" read the spacing exists to give. The gap between the tab strip and the first card uses the SAME value, not a bigger one invented just for that seam — one number, reused, beats two numbers that happen to look similar. First measured live in BombVault's own Settings page (bumped from `gap-6`, once the largest gap value anywhere in that app, to `gap-10` for both the card-to-card wrapper and the tab-strip-to-first-card wrapper in the same round).

## The tooltip and info bubble

Two triggers, **one shared engine** — [`reference/tooltip.ts`](../reference/tooltip.ts)'s `wireTooltips()` + `infoIcon()`. A plain icon-only button's hover tooltip and a control's "(i)" explanatory bubble are the same mechanism wearing two different trigger elements, not two separate implementations that happen to look similar. An app that built its own bespoke bubble (its own positioning, its own CSS, no arrow, no flip) alongside a *different* implementation for tooltips is the exact inconsistency this section exists to rule out — found in production: one adopting app's info bubble and its toolbar tooltips visibly disagreed on background colour, corner radius and shadow depth because they were two unrelated pieces of code.

- **One floating bubble, `#glim-bubble`, a single `<body>` child** — not a per-trigger popup. `wireTooltips()` positions and fills the same element for whichever trigger is currently hovered or focused, `reference/tokens.css`'s `.glim-bubble` styles it. Rendered into `<body>` (position measured from the trigger's own `getBoundingClientRect()` in JS) so no scroll container, card or table can clip it — an anchored-locally popup is at the mercy of every `overflow: hidden` above it, and one card's own clipping shouldn't be able to turn an explanation into a sliver.
- **`data-tip` is the one attribute that drives it**, on either kind of trigger — a plain icon-only button (`<button data-tip="Undo">`) or the "(i)" glyph (`infoIcon()` sets it internally). **A stray native `title=` anywhere in the app is auto-upgraded to `data-tip` on its first hover** (`wireTooltips()`'s delegated listener does this, then removes the `title` so the OS's own balloon never also fires) — adopting the engine is one `wireTooltips()` call at boot, not a rewrite of every existing tooltip call site.
- **Viewport-clamped, flips above the trigger, has an arrow.** Opens below the trigger by default, centred on it; clamps horizontally into the viewport with an 8px margin so a trigger near either edge doesn't push the bubble half off-screen; flips to open **above** when opening below would clip the viewport's bottom edge (and only then, and only if there's room up there). A 6px CSS-triangle arrow points from the bubble back to the trigger, tracking the trigger's real position (`--glim-tip-ax`) even when the bubble itself has been clamped off-centre.
- **Never partially clipped by the viewport, full stop — a requirement, not a preference.** A bubble rendering even one pixel past any edge of the browser window has failed at its one job: being read. Reported live, by name: BombVault's own `InfoBubble`/`SelectorTab` — the exact component the "Cross-app info-bubble standardisation" entries elsewhere in this document call the anointed reference implementation — had in fact never implemented any of the clamp/flip behaviour this section already documented. Both call sites positioned the bubble by centring it on the trigger (`left: r.left + r.width / 2`) and always opening downward (`top: r.bottom + 6`), with zero viewport awareness at all; the gap had simply never been exercised by a trigger near enough to an edge. Surfaced as the "Wiederherstellungskit" (Recovery kit) info bubble in Settings, whose own longer-than-average tip wraps tall enough that a trigger anywhere past roughly the vertical midpoint of a normal-height window pushes the bubble's bottom past the window edge. Fixed by porting `reference/tooltip.ts`'s own `show()` math — pixel for pixel, 8px margin, clamp-then-flip — into a small shared, pure, unit-tested function both call sites now invoke from a `useLayoutEffect`, measuring the bubble's REAL rendered size (not an assumed constant, since height depends on how many lines the tip wraps to) before it ever paints. A second, sharper gotcha surfaced while stress-testing that fix at a narrow viewport: `.glim-bubble`'s `width: max-content` (already specified above) isn't cosmetic — it's load-bearing for any measure-then-position approach. Without it, a `position: fixed` box with only `left` set sizes itself via CSS shrink-to-fit, whose available width is `containing-block-width − left`; the box's own rendered width silently depends on wherever `left` ends up. Compute a clamped `left` from a measured size, apply it, and the box can then change its own width and (via rewrapping) height in response — invalidating the very measurement the position was based on. Confirmed live: a bubble shrank from 280px to ~155px wide and grew from ~126px to ~253px tall AFTER being positioned, fitting its viewport only by chance in that one case. BombVault's own shipped `.glim-bubble` was missing this property despite standing here as the documented recipe — corrected there, and recorded here as a hazard any adopter doing measure-then-clamp positioning in a component framework (rather than `reference/tooltip.ts`'s own single always-in-DOM element) needs to know up front, not rediscover live.
- **A 110ms opacity fade on open (`.glim-fade` / `glim-fade-in`), instant on close.** Short on purpose — a bubble that fades in slowly reads as *lag*, not *polish*, because the pointer is already there waiting for it (see "The motion engine" below, which this section now agrees with — an earlier draft of this bullet claimed an instant, un-animated `display` toggle instead, which was simply wrong: `.glim-fade` already existed in `reference/tokens.css` and the reasoning below always said 110ms, the toggle just wasn't wired to it yet). Closing has no fade — the bubble should get out of the way the moment it's no longer wanted, the same asymmetry `.glim-toast` doesn't share (a toast is content arriving and leaving; a tooltip is a hover-driven aid that should vanish the instant that hover ends).
- **Hover *and* focus** open it (`mouseover`/`focusin`, delegated on `document`, not per-element listeners); a `pointerdown` anywhere, **Escape**, or any scroll hides it immediately — a press means the person is acting, not reading, a scroll de-anchors the fixed-position bubble from whatever it was pointing at, and Escape lets a keyboard user dismiss it *without* moving focus off the trigger.
- **`pointer-events: none` on the bubble itself** — it never swallows a click meant for whatever's underneath it once it's already open.
- **The info icon (`infoIcon()`) is a bare stroke-only SVG glyph, never a filled badge.** Neutral colour, `opacity: .8` at rest → `1` on hover/focus — the icon is furniture; a background fill on it would read as a control it isn't (rule 3: the accent, and by extension any fill, means activity). **`:focus-visible` draws a real 2px solid `--focus-ring` outline, 2px offset** (the same treatment every ordinary button and link already gets from the base `:focus-visible` rule) — **the info-bubble trigger's `:focus-visible` outline is a deliberate, sole exception to this design language's "never border lines" rule (rule 5) — keyboard-focus visibility on an otherwise-borderless glyph is worth the one exception; mouse/hover interaction never shows a border.** Opacity alone doesn't clear that bar: `.8 → 1` reads identically to plain hover, so a keyboard user tabbing to a glyph with no chrome of its own had no reliable way to tell it was focused before this outline existed — a real WCAG 2.2 SC 2.4.7 gap, not a style preference either way.
- **A tooltip only exists when it adds information the trigger doesn't already show.** An icon-only button (no visible text at all) needs one unconditionally — there's no other way to know what it does. A control that already shows its own full label as visible text does NOT get a tooltip repeating that same text verbatim; the one case where a *labelled* control still earns one is when its own label is actually truncated (an ellipsis-cut string in a fixed-width segmented option, say) and the tooltip is the only place the full text still exists. Found in production: a Rotate control's own segmented buttons (already showing "0°"/"90°"/"180°"/"270°" as visible text, never truncated) carried a tooltip repeating the exact same four characters back — pure noise, while a sibling Flip control's icon-only buttons had no tooltip at all and genuinely needed one.

Why bother at all: grey prose under every control gets read once and then costs vertical space forever.

## The time picker

Hour and minute get the same treatment "The user-owned axes" already gives colour: never hand off to a native OS surface a page can't style or verify. A native `<input type="time">` renders its own browser/OS spinner UI entirely outside the page's DOM — unstylable, unverifiable in automated testing, and (BombVault, live-review) exactly the kind of manual-typing field jdp keeps asking to eliminate: *"Können wir bei den Zeitfeldern einen schönen Stunden- und Minuten-Picker implementieren, damit man es nicht manuell eintippen muss"* — a nice hour/minute picker so the value never has to be typed by hand. Replace it with the same shared portal-popover machinery "The tooltip and info bubble" already established, wearing a third trigger shape (a compact "HH:MM" field-button) alongside that section's icon-only button and "(i)" glyph.

- **The trigger shows the value, never accepts typed input.** A plain field-styled `<button>` — not an `<input>` — displaying the current "HH:MM" as read-only text; the whole point is eliminating manual entry, so nothing about the trigger itself should invite it. Keeps the exact visual footprint of whatever field it replaces (BombVault's version reuses the identical classes its sibling cron/every-N inputs already carry) so swapping one field type for another doesn't visually orphan it from its row.
- **Two independently scrollable `role="listbox"` columns, not a pair of native `<select>`s.** Hour (0–23) and minute (0–59, in configurable steps — 5-minute increments is a sensible default for anything schedule-shaped, since a backup cadence rarely needs to-the-minute precision) sit side by side inside the popover, each a real, always-visible scrollable list rather than a second click-to-open dropdown nested inside the first. This is the language picker's own "custom-listbox escape hatch" (see "The user-owned axes" above) applied to a NUMERIC column instead of a short fixed list — the same underlying answer (build a real listbox when a native form control can't give the styling/verification control needed) to what is otherwise a differently-shaped problem.
- **Reuses the tooltip engine's own positioning contract, not a fourth clamp implementation.** Portal-rendered to `<body>`, measured off the trigger's own rect, viewport-clamped with an 8px margin, `transform: translateX(-50%)` + `width: max-content` for the same reason "The tooltip and info bubble" already documents that exact pairing as load-bearing (a box sized by CSS shrink-to-fit before being positioned invalidates the very measurement the position was based on). An app that already has more than one hand-rolled popover-clamp implementation living side by side — a tooltip's own math, a colour picker's own separately-coded clamp (see "The user-owned axes" > Accent above, whose `openColorPickerPopover` predates the shared positioning function and still carries its own copy) — should call the ONE shared function for the next one instead of adding a third copy; BombVault's time picker does this correctly.
- **Dismissal: outside pointerdown, Escape, or a scroll/resize of anything OUTSIDE the popover — not literally any scroll event.** The colour picker's own contract ("closing on outside click, Escape, scroll or resize") is right for a popover with no internal scrollable region of its own, but a time picker's two listbox columns genuinely need to scroll — bringing the current hour/minute into view on open, or as arrow-key navigation moves past the visible window — and a naive capture-phase `window` scroll listener catches THOSE internal scrolls too, since a capturing listener on an ancestor receives every scroll event on the way down to its real target regardless of whether that event bubbles. **Found in production (BombVault, live against a real deployed container — jsdom's own tests never caught either bug below, since jsdom doesn't simulate the browser behaviour involved): the popover closed itself roughly 2ms after every single open**, confirmed via a live `MutationObserver` showing the trigger's `aria-expanded` flip `true` then `false` again almost instantly, the closing scroll event's own target being the internal listbox column, not the window. A second, related trap compounded it: moving keyboard focus into the popover's first option **before** its real on-screen position had actually been committed and painted (it briefly sits at an off-screen placeholder coordinate while the position is only just being measured) makes the BROWSER auto-scroll trying to bring that off-screen element into view — which then trips the very listener above, a second, independent path to the same self-closing symptom. Fix both by (a) gating any `scrollIntoView`/`focus()` effect on the real position already being known, not merely on "open," and (b) checking the scroll event's own target and ignoring it when that target lives inside the popover's own panel — a scroll INSIDE a popover never de-anchors it from its trigger the way an ancestor/page scroll does; only the latter should close it.
- **Shape and colour engines, wired in as it's built** (the standing rule under "Shape" above: *"A new component is wired into both engines AS it's built, not audited in afterward"*) — the trigger and popover read `--radius-control`/`--radius-card` like every other field/card in the app, and the popover's selected-hour/selected-minute highlight reads `--accent`/`--accent-contrast` directly. A standalone field-replacing control, not a row in an enumerable list, so it takes the flat single accent by default the same way the colour picker's own swatch trigger does (see "The user-owned axes" > Accent above), while still accepting an optional palette-position index for a future call site that DOES sit in a hue-indexed list, through the exact same `hueVars()`/`.glim-hue` mechanism "The one horizontal selector"'s segments already use — `[data-rainbow] .glim-hue` redefining the plain `--accent`/`--accent-contrast` custom properties for any element carrying that class means the SAME selected-state rule composes automatically the moment a future consumer opts in; no second, hue-specific rule needs to exist for that composition to work.
- **Forced `dir="ltr"`, matching every other technical value under RTL** (see "Right-to-left languages" above) — a clock reading like "14:30" is data, not prose, and stays left-to-right on both the trigger and the popover even when the surrounding page mirrors for Arabic or Hebrew.
- **Fully keyboard-operable with no typing at all.** Arrow keys step the focused column and commit immediately (the same "arrow-selects-as-it-moves" convention "The one horizontal selector" already uses for a single-choice strip); Home/End jump to a column's ends; left/right arrow keys move focus between the hour and minute columns; Escape closes it; Enter/Space on any option already work for free since every option is a real `<button>`. Only ONE popover of this kind is ever open across the app at once — the same singleton rule the colour picker already establishes.

First built for BombVault, replacing every native `<input type="time">` in the app.

## The one horizontal selector

Tabs, filter bars, segmented controls and the corner-style picker are **the same thing**: a row from which one (or several) item is chosen. Build it as **one** component (`select="one" | "many"`, built from a filled/unfilled segment style), not a bespoke set of buttons per picker — a second, hand-rolled selector drifts from the first one the moment either changes. This is for **small, fixed** sets that all fit on screen at once — a list with dozens of entries (see the language picker below) is a different component, not a wrapping tab strip.

- **No wrapping bar.** The filled tab already says which one is selected; a box around the row says nothing and is one elevation too many (rule 1). The container is gone entirely; the gap alone carries the separation. Measured: a bare strip, no background, no padding.
- **Every tab is a badge, not just the selected one.** "The tabs sit on the page as badges" means literally that — an unselected tab still carries its own quiet fill (`bg-carbon-surface2`, no border) so it reads as a distinct pill at rest, not as bare text floating on the page that only gains a shape once picked. An early build read this rule as "bare until selected" (zero background at rest, `bg-carbon-hover` only on actual mouse hover) — the resulting strip looked unfinished on a settings page with a dozen tabs, most of them plain text. The gap between tabs still carries the separation either way (no wrapping bar); the badge fill is per-tab, not a strip-level container.
- **Every tab is the same width**, sized to the longest label in the set rather than to its own content — a strip where each tab hugs its own text reads as a ransom note, not a row of equal-weight destinations.
- **That target width is shared across every equal-width selector instance in the app, not computed independently per strip.** Measuring only the widest label *within* one strip (the bullet above) makes that one control internally consistent, but says nothing about how it compares to every OTHER equal-width selector on the same page — a 7-tab settings bar, a 2-option theme picker and a 3-option shape picker, each converging on its own different widest-label number, still reads as three unrelated controls of three different sizes, not one recurring pattern; none of them individually looks *wrong*, but the app as a whole doesn't read as having one selector style. Fold a single APP-WIDE floor into the same per-segment measurement instead of computing it in isolation: `Math.max(ownWidestSegment, MIN_WIDTH)`, where `MIN_WIDTH` is one shared constant, picked once, comfortably above the single longest label across *every* equal-width selector instance in the app — not just the strip currently being sized. This still isn't the "hand-picked number" the bullet above rules out: the segment width is still a real DOM measurement, `MIN_WIDTH` only adds a floor beneath it, and a strip whose own content genuinely needs more than that floor still gets its own larger measured value — never clamped down. Verbatim, live-review, one round after the "sized to its own content" fix landed: *"Die horizontalen Selektoren bitte breiter und möglichst gleich breit"* — wider, and as equal-width as possible, not just each one narrow-and-content-hugging in its own private way. Calibrated live in BombVault: the app's own single longest label anywhere in an equal-width selector ("Benachrichtigungen," the Settings tab strip) measured 174px at its stage's own type/padding; a round 200px floor clears that with real headroom, and pins the Theme Card's two-option well (previously 97px, driven by "Dunkel" plus its own icon) and the Shape Card's three-option well (previously 62px, driven by "Leicht") up to that same 200px too — all three now render literally identical, not merely closer, because none of the app's three call sites has a label that genuinely needs more than 200px today. Recalibrate the constant, not the mechanism, if a future label ever legitimately needs more room than the current floor provides.
- **The strip itself is sized to its own content, never stretched to fill its container.** A horizontal selector's row is a flex container; left unwrapped inside an ordinary block-flow parent, or as a bare flex ITEM inside a column that stretches its children (the default `align-items: stretch`), it silently expands to the ancestor's own full width the moment nothing opts out — a strip meant to read as "a small, tight, purposeful control" instead reads as "one control stretched edge-to-edge across an unrelated container." Wrap it in a box that opts OUT of the inherited stretch (`display: inline-flex` + `align-self: flex-start`) rather than capping it with a guessed pixel value — `inline-flex` alone isn't enough once the parent is itself a flex/grid container, since a flex/grid child is always blockified regardless of its own declared display, so `align-self` is the part that actually does the work. The strip then hugs whatever width its own (equal-width) segments genuinely need, growing or shrinking with the label set, the active locale or a font change, instead of a hand-picked number someone has to remember to update. Found live: an app's Theme and Shape pickers were both bare flex children of a card's own `flex flex-col` body, stretched to the full card width by the column's default cross-axis stretch — invisible until the fix for something else (removing an intentionally-wide tab strip's own full-width treatment) made the same un-wrapped default suddenly visible on every OTHER selector in the app too.
- **Top, with an icon — every single one, no exceptions.** Settings pages line their tabs up **horizontally at the top**, each with a glyph. A tab with no label is a gap; a tab with the wrong glyph is a lie — no icon beats the wrong one. A tab shipped without an icon "for now, add it later" is the exact drift "Icon glyphs" (below) warns about in miniature: an audit later finds one tab that never got one, not zero.
- **It wraps, it never scrolls.** A horizontally scrolling tab strip hides pages behind a gesture nobody makes on desktop.
- **Roving tabindex**, arrow keys/Home/End, direction-aware (RTL).
- **Under rainbow, only the SELECTED segment owns a position** — see "Rainbow — the accent, plural" below. The fill already carries the selection state; colouring every segment (including the ones not picked) is noise the control doesn't need, unlike a list row (which needs a wash at rest or an all-idle list shows no colour at all).

**The trap:** `Field` is a `<label>`. A label wrapped around *three* tabs hands its click to the first one — clicking the "Corners" caption reset the app to "round", and the first tab announced the caption as its own name to a screen reader. So: `Field` for **one** control, **`FieldGroup`** for a set.

**A second styling: the well.** The default above ("no wrapping bar... the container is gone entirely") is right for a strip that reads as a row of independent badges — but a genuinely EXCLUSIVE, small, closely-related set (three shape options, an on/off/reactive triple) can instead sit inside one shared padded "well" track (`background: var(--carbon-surface2)`, `padding` and inter-segment `gap` both `0.2rem`, `border-radius: var(--radius-control)` on the track itself, segments flush with no radius of their own), with the active segment filled (`background: var(--accent)`, `color: var(--accent-contrast)`) and a plain `background-color` crossfade — no sliding pill/thumb — on change. This is a genuine second, opt-in styling of the SAME component (a `variant` on the one selector, not a second implementation), not a replacement for the default: the well reads as "one control with N settled positions," the bare-badge default reads as "N independent, equally-weighted destinations" — pick per call site by which of those two things is actually true. First built for BombVault's shape picker (round/soft/square), adapted from a shared "segmented row" widget already used the same way in TrickWork.

**A live trap once the well track stops being handed extra width by an ancestor (see the "sized to its own content" bullet above):** if the well's own equal-width segments come from plain flex-grow shares (each segment `flex: 1`, i.e. `flex-basis: 0%`) rather than a real measurement, removing the ancestor's stretch can silently truncate the WIDEST segment's own label. A flex item whose `flex-basis` resolves to a definite value (`0%` counts) contributes that zero — not its own content width — to a shrink-to-fit ancestor's intrinsic-size calculation, so the track ends up narrower than its widest segment actually needs the moment nothing forces it wider. The fix is the same real DOM measurement the plain "every tab is the same width" bullet above already needs for a bare-badge strip: measure the widest segment's own natural content width, then pin every segment (well or bare-badge alike) to that literal pixel value via inline style — `flex: none` plus an explicit `width`, never a `flex: 1` share. Found live: a two-segment well (light/dark) truncated its longer label to a bare ellipsis the moment its own ancestor stopped stretching it, confirmed via `scrollWidth` genuinely exceeding `clientWidth` on the label span — not a font-rendering artifact. Same keyboard/RTL/disabled rules as the default apply unchanged; only the paint differs.

## The sidebar

A persistent left rail is how a multi-destination app is navigated: the brand mark at the top, a vertical icon+label list filling the middle, and Settings pinned at the bottom below a spacer — no separate top app-bar at all, the brand lives inside the rail. This is a **different component** from the horizontal selector above, not a vertical variant of it: a sidebar destination is real navigation (which whole content area is showing), not "which of a small fixed set is chosen" — it uses `aria-current="page"` semantics, not the ARIA tabs pattern, and in an app without a URL router it's the same idea an SPA reaches for when it swaps a content area without touching the address bar.

- **Own surface token.** The rail reads `--carbon-sidebar`, not `--carbon-surface` — same value today, but a distinct token, because the rail is chrome that spans full height flush against the window edge, not a card floating on the ground colour. No elevation, no border: the page's own background colour change *is* the separation.
- **Filled when active**, same idea as the horizontal selector: the accent fills the active item (`background: var(--accent)`, `color: var(--accent-contrast)`), nothing else marks selection — no rail-beside-the-rail, no left border (rule 5 already forbids vertical marks generally, and a sidebar is exactly where the temptation to add one is strongest).
- **Idle is coloured, always, unless Reactive mode is on.** A not-yet-selected destination shows its own colour on its icon at rest in Normal and Rainbow mode alike, no hover required — see "The tab-strip colour rule" below, which this rail shares with the horizontal selector's own tabs. Only in Reactive mode does idle go neutral, with hover revealing that same colour again.
     **REVERSED** (jdp, live-review, one round after this rule first shipped as "the rail never routes a rainbow position": *"Die ganzen Tabs in der Sidebar sind wieder nicht im Regenbogenmodus bzw in der Farbengine."*) — the rail routes a genuine rainbow position now, exactly like the horizontal selector's own tabs: `.glim-hue`/`.glim-hue-icon`, `hueVars(rainbowAt(index))`, the identical mechanism, on the identical element. The original objection here (preserved for history: a destination list is user-configured and its length/order can change on any render, so a STATIC literal index could never hold a stable position) turned out to be an objection to a *static index*, not to a rainbow position as such — the fix resolves that index from a `nextHue()` counter, incremented once per destination DIRECTLY in the order it actually renders (the same pattern a dashboard's own conditionally-rendered block list, or a settings page's own conditionally-rendered tab panels, already use for their own headings). A conditional destination that is hidden this render never consumes a slot, so hiding or showing it never disturbs the position — and with it the colour — of any destination that does render. A genuine set-of-ONE elsewhere in the same rail (a mode toggle with no sibling of its own kind, say) is the one thing this still doesn't apply to — see "Rainbow — the accent, plural" below for that general exclusion.
- **A quiet hover moves, it doesn't just recolour.** A 2px horizontal nudge on hover (motion-safe-gated) reads as "this is reachable" more than a colour change alone does on a rail this visually quiet.
- **Two groups, one state.** The main destinations fill the available height (`flex: 1` on the list); Settings sits in its own group below, separated only by the space the flex spacer creates — never a rule line between them (rule 5 again). Both groups share one "which destination is active" state; only one content area is ever showing.
- **Version numbers live in Settings, never in a persistent footer** — and specifically at the **very bottom of the Settings destination itself**, outside every card, not tucked inside whichever card happens to be last. A version string sitting in permanent page chrome is read once and then costs a line forever (the same objection rule 8 makes about explanatory prose), so it belongs where someone actually goes looking for it; putting it inside one particular card (Appearance, say) makes it read as *that card's* property instead of the whole app's, and ties its position to wherever that card happens to land if Settings ever gains or reorders cards.

**A lightweight alternative for a genuinely simple app.** Not every adopter has enough real destinations to justify a full rail — a single-workspace tool with only "the work" and "Settings" can skip the sidebar entirely and put a small square badge (`--radius-control`, not the pill) carrying a gear glyph in the page's own top-right corner instead, opening Settings as its own full-page view (still no preview, no working cards behind it — see rule 15, a window is a window). This is a real, sanctioned pattern, not a workaround: state which one an app uses and why in that app's own style-guide subnote, since a future pass shouldn't "fix" a deliberately simple app back toward the rail.

## The tab-strip colour rule

A tab — a horizontal-selector segment, a sidebar destination, anything from "one of a small fixed set is currently chosen" — carries colour in exactly one place at a time, and which place depends on BOTH interaction state and rule 9's own colour mode: **idle is colourless only in Reactive mode — in Normal and Rainbow mode idle already carries colour, always, no hover required. Hover reveals the icon's colour in Reactive mode (a no-op in the other two modes, since the icon is already showing it); selection fills the badge and puts the icon back to plain contrast ink, in every mode.** Verbatim, live-review (jdp, both the horizontal selector's own Settings tab strip and the sidebar's main nav) — the original ask: *"Die Tabs sollen nicht ausgewählt farblos sein. Beim Mouseover soll das Icon eingefärbt werden und wenn man sie anklickt soll der Badge eingefärbt werden und das Icon wieder in schwarz oder weiß angezeigt werden."* — and a follow-up correction one round later, once the first implementation over-applied that ask to every mode instead of Reactive alone: *"Die Icons der Haupttabs in der Sidebar und die der Tabs in den Settings sollen immer farbig sein, wenn der reaktive Modus ausgeschaltet ist."*

This is a genuine three-state machine per tab — idle / hover / selected — layered ON TOP of rule 9's three colour MODES (normal-rainbow / reactive-rest / reactive-hover), not a restatement of it and not independent of it either. Rule 9 decides WHETHER colour is showing right now for the active mode, always painting the *same* visual role (a badge's fill, a switch's track, an icon's own tint) once it decides yes; this rule decides WHICH PART of the control gets that colour, because the answer changes as the same tab moves through idle → hover → selected — but the idle/hover half of that split only actually happens in Reactive mode, the one mode where rule 9 itself ever puts colour on hold. In Normal and Rainbow mode rule 9 never rests at all, so this rule's "idle" state is never truly colourless there — it only *looks* colourless if the implementation mistakenly ties the icon's colour to a hover/focus condition regardless of mode, which is exactly the bug the follow-up quote above reports. An icon-only toggle badge (rule 9's own "icon-only TOGGLE" bullet) already established half of this precedent — the glyph never carries colour, only the badge does, once checked — but a tab's icon *does* carry colour, in every mode except reactive-rest, moving only in Reactive.

- **Idle: colourless in Reactive mode only.** A not-yet-selected, not-currently-hovered tab reads as neutral **while Reactive mode is on** — with rainbow off, or plain "on," that same idle tab already shows colour (the flat accent, or its own rainbow position where the control owns one) with no interaction needed at all. (This is orthogonal to "every tab is a badge, not just the selected one" above — that rule is about the badge's neutral *shape* existing at rest, `bg-carbon-surface2`; this rule is about that same badge's ICON, and only goes neutral in the one mode built to rest.)
- **Hover (an unselected tab only): the icon tints, in Reactive mode.** The glyph picks up this tab's own colour — its rainbow position where the control owns one (the horizontal selector's tabs, and the sidebar's own destinations too — see "The sidebar" above for the reversal that gave the rail a genuine position of its own), or the single flat accent for the rare genuine set-of-one that owns no position at all. In Normal/Rainbow mode the icon already shows this colour before the pointer arrives, so hover changes nothing there — the reveal is Reactive-specific, not a universal hover effect layered on top of every mode. The badge's background stays whatever neutral hover treatment it already had in every mode.
- **Selected: the badge fills, the icon reverts to contrast ink — in every mode.** Same colour the icon was already showing (hover-revealed in Reactive, always-on in Normal/Rainbow) — this tab's own hue, or the flat accent — but now on the BADGE, with the icon reading `currentColor` off the badge's own contrast token (`--accent-contrast` / `--item-hue-ink`) instead of the hue itself. Painting the icon in its own hue on top of a badge already filled with that hue would make it vanish into its own background — the same reasoning rule 9's icon-only-toggle bullet already gives for why a checked badge's glyph stays plain.
- **Each tab keeps its OWN colour across all three states.** Whichever hue (or the flat accent) a tab shows at idle-or-hover is the exact same one its badge fills with once selected — the position is a fixed property of the tab, hueVars()/`--item-hue` assigns it once, and this rule only changes WHEN and WHERE that already-fixed value gets painted, never what it is.

**Implementation note, not a new mechanism:** where a control already carries a rainbow position (`.glim-hue`, hueVars()), reuse the exact `--accent`/`--item-hue` cascade rule 9 already resolves correctly in every mode — the icon's "coloured" declaration itself stays UNCONDITIONAL, no interaction gate and no rainbow-mode gate at all, so it simply reads whatever `--accent` already resolves to on that same element (the flat accent in Normal, this item's own hue in Rainbow) with no extra CSS needed. Only Reactive mode needs its own explicit pair of rules layered on top of that unconditional one — one resting the icon back to a neutral muted token at idle, one restoring `var(--accent)` on `:hover`/`:focus-within` — mirroring `[data-rainbow="reactive"] .glim-hue`'s own existing rest/hover split for the base hue mechanism, since that block's `--accent` swap alone doesn't keep an ICON's separate idle-vs-selected exclusion (`:not(.glim-active)`) straight on its own. This is now the ONE rule every hued tab strip shares, the sidebar's own destinations included (see "The sidebar" above for the reversal) — a control with genuinely no stable position at all (a set-of-one, e.g. a lone mode toggle with no sibling of its own kind sitting in the same rail) is the one remaining case that skips `.glim-hue` entirely and reads the flat `--accent` token directly, needing that same Reactive-only rest/hover pair restated explicitly on its own class rather than inheriting one from a `.glim-hue` it never carries.

**The trap this replaced:** an earlier pass wired the icon's "coloured" declaration to `:hover`/`:focus-within` directly and dropped every mode gate outright, reasoning that leaning on `--accent`'s own per-mode value would cover every case for free — it does, but only once the icon actually READS `--accent`, and gating that read behind `:hover` left every idle tab colourless in Normal and Rainbow mode too, not just Reactive (Reactive was the only mode that was ever supposed to withhold colour at rest). The fix was never "make hover reveal colour" — that part already worked — it was "stop requiring hover to see colour at all outside Reactive mode," by making the coloured declaration unconditional and pushing the rest/hover swap down into a Reactive-only override instead of being the only path to colour in any mode.

First implemented in BombVault: the Settings tab strip's `.glim-hue-icon` and the sidebar's own analogous rule. CORRECTED one round later from that unconditional-`:hover`-gated version (idle colourless in Normal AND Rainbow mode, not just Reactive) to the mode-aware version described above. RE-UNIFIED a further round later, once "The sidebar"'s own rainbow reversal (above) gave the rail a genuine position of its own: the sidebar's separate "analogous rule" mentioned above is now literally `.glim-hue-icon` itself, not a second copy of it — the rail's destinations became one more consumer of the SAME rule the Settings tab strip's own Selector segments already used, with no new CSS written for the rail at all. The rail's OWN copy of this rule survives only for its one remaining set-of-one control (see the implementation note above).

## Switches

- **Flush, no indent.** Sub-switches don't get indented — they're already dimmed when the parent switch is off, and that says the relationship better than indentation does. Indenting only left the switch tracks starting at two different x-positions.
- **A switch always shows its own label text — never rely on a heading above it to say it instead.** Hiding a row's own caption on the reasoning that a Card's title (or a sub-heading) directly above already states the same thing reads, at a glance, like the harmless case `hideLabel` exists for — but it is not: it leaves the actual control sitting there with no visible name of its own, discoverable only by scrolling up and reading a heading that happens to describe it. This exact shortcut was tried and reversed three separate times in one project (BombVault: the Rainbow section's master "Regenbogen-Modus" toggle, RestoreChecksSection's "Automatische Restore-Prüfungen" toggle, and the notifications tab's weekly-digest toggle) — each time built on the "single-purpose Card whose title IS the decision" reasoning, each time reversed once someone actually looked at the row and saw a bare switch with nothing next to it — before the fourth occurrence (a metrics-enable toggle, a Flash-ZIP-export toggle, and a "Quiet toasts" toggle, found in one full-app audit after the third reversal) finally got the underlying prop deleted outright rather than patched yet again. `Toggle`'s own `hideLabel` keeps exactly one legitimate, narrower job: a caller that already draws this identical text ITSELF, right there in its own layout — a hand-rolled row with its own caption `<span>`, or a wrapping `<label>` with a sibling `<span>` — tells the bare switch not to print a second, literally duplicate copy beside the one already on screen. "A Card title further up the page already says it" is never that caller — a heading and the control it introduces are not the same layout position, and the gap between them is exactly where a screen reader user, or anyone who landed mid-page, finds nothing. **Never a reason to skip the label entirely** — a nameless switch is a control nobody can describe.
- **Switched off, not hidden.** A control that disappears never teaches anyone what the mode does.
- **Glyph, not a colour swatch.** The corner-style picker shows its radius as an **outline** in the text colour (`border-[1.5px] border-current`), not a filled accent square: three coloured dots beside three captions is decoration, and the accent means activity (rule 3).
- **The knob follows the shape engine too, not just the track.** A switch's sliding knob is a small rectangle wearing a corner radius like every other shape-engine surface — round → a true circle, soft → a lightly-rounded square, square → sharp corners — reading `--radius-pill` the same token the track already does, not a hardcoded `rounded-full`. This is `Toggle`'s own single shared component, so the fix lives there once and every switch in the app picks it up automatically — the same "fix it where the shared component lives, not per call site" shape as the shake pattern above. Found missing after shipping: a switch this small is exactly the kind of element easy to leave circular "because it always has been," even in an app that already got every larger surface right.

## Saving

A settings field persists itself the moment it changes — no batched "Speichern" button gating an ordinary edit, and nothing an "unsaved changes" warning has to protect on the way out. This is the same reasoning "Destructive and confirmable actions" already applies to removal (a reversible action doesn't ask) turned around for edits instead of deletes: a toggle, a schedule, a path is independently valid the instant it's set, so a batched commit step in front of it isn't guarding anything the field's own edit doesn't already guarantee by itself.

Two shapes, chosen by how the control fires — not by which field it happens to be:

- **A discrete action (a switch, a pick from a small fixed set) auto-saves immediately, with revert-on-failure.** Flip it and the UI updates optimistically right away; the PATCH that used to wait behind a Save click now fires on the spot. If the backend refuses (a real precondition the UI can't check in advance — no SSH connection configured for a feature that needs one, say), the control snaps back to its prior value and plays `glim-shake` (see "The motion engine") — the exact refusal signal this language already uses everywhere else an optimistic UI action gets undone. The reason surfaces through the ordinary toast, never a second inline error state bolted onto the control itself. This toast+shake pairing isn't specific to auto-save fields — see "Failure feedback" below for the same rule applied to every OTHER failable action in the app, including a plain button with no optimistic value to revert at all.
- **A continuous input (free text, a number field, anything that fires on every keystroke rather than on selection) debounces instead, and does NOT revert.** Saving on every keystroke is wasteful (a cron expression, a path, a hostname are each typed one character at a time) and would race a mid-type PATCH against the very state it's reading from. Wait until the input goes quiet (BombVault uses 800ms) and save the field's current value once. No revert on a rejected save here: the value on screen is the value someone just typed, and snapping it to something else while they might still be correcting it is worse than leaving it as-is and letting the toast carry the failure — the next edit, or a reload, gets another chance to save it correctly.

Both shapes call the exact same persistence primitive underneath — one PATCH that merges a single field's change onto the server's own current baseline, never the client's possibly-stale full copy of it — so the split above is only in how the trigger reaches that call, never a second save mechanism living alongside the first.

**When a manual "Speichern" button is still the right answer:** not in front of an ordinary field, and "that's just how this page has always worked" isn't a reason — a Save button still gating a plain toggle or text field on a page nobody has migrated yet is legacy, not a deliberate exception, the same way an un-migrated hardcoded radius value looks correct right up until someone actually switches shape and it doesn't move (see the shape-engine bullet under "The user-owned axes" — "looks fine at a glance" and "is actually wired correctly" are different claims). A manual commit step earns its place only where what's being persisted genuinely ISN'T "one field, valid the instant it's set" — four shapes have actually earned it so far, not a checklist to satisfy but the real reasons found so far when a page's remaining Save buttons were each individually interrogated rather than grandfathered in:

- **A multi-field submission that would leave the backend in an invalid halfway state if committed one field at a time** — adding a brand-new target whose several fields only make sense together, say. The sharper tell than "the backend state would be invalid" is behavioral: this shape almost always sits behind an explicit Cancel/Close that genuinely discards the in-progress draft, and auto-saving on the very first keystroke would silently defeat that affordance the instant it fired — a half-typed name would already exist as a real, visible row before the user ever meant to commit it. If Close doesn't actually reset the draft back to nothing, there's no affordance to protect and the field should auto-save like any other (BombVault's ItemScheduleOverride — its own collapse/expand toggle only hid the editor, never discarded `value` — failed this test and converted; its two genuine siblings, CloudCredSetsCard's and OffsiteTargetsSection's own "add a new one" editors, both reset their draft to nothing on Close and kept their buttons). A field merely being "part of a bigger form" isn't enough on its own — check whether Close actually discards anything before granting the exception.
- **A control that TRIGGERS an operation rather than persists a preference** (run this now, send a test message, rotate a credential) — which earns its own imperative-verb label ("Run now", "Send test") rather than a bare "Speichern" borrowing the wrong pattern.
- **A field that is a one-shot, write-only "apply this" action with no live current value to sync** — the box never round-trips what's actually stored (blank on every load, blanked again after a successful apply), so there is nothing for auto-save's optimistic-update contract to even describe, and the apply itself wholesale-REPLACES a config some unrelated autonomous process (a scheduled job) reads on its own clock — a mid-edit auto-fire would hand that process a momentarily broken blob instead of the working one it had a moment ago. (BombVault's rclone-config paste box: pasting a NEW config to add a remote, never editing the CURRENT one in place.) A field that instead shows the real persisted value and merely happens to live in a whole-object POST rather than a partial PATCH does NOT qualify — that's just an implementation detail the field's own auto-save wrapper absorbs (see CloudCard/NotifyCard below).
- **A field whose validity depends on agreeing with a SIBLING field before the write is even safe to attempt**, with no sane per-keystroke trigger — a password-plus-confirm pair: auto-saving the first field alone persists a credential nobody finished typing, and auto-saving on every keystroke of the second spams a mismatch failure until the two happen to agree. Doubly justified when the value being written takes effect immediately and controls access to the whole instance — the closest thing to "rotating a live credential" this exception list already names elsewhere, and the reason a login password is the one field on a settings page most likely to keep its button.

First applied across BombVault's Settings page over several rounds — the Domains card (each domain toggle saves itself the instant it's clicked, live-showing/hiding that domain's own nav tab with no reload), two Paths & Storage card merges (a mix of immediate-toggle and debounced-text fields sharing one card), and the Schedules tab (every cadence picker, every offsite/self-backup cron field, and the two new "per-item schedules"/"sync to Containers" toggles) — before being written down here as the standing rule once the same shape had proven itself on four genuinely different kinds of fields, not just one. A later full-page sweep closed out every remaining manual button across that same Settings page's other tabs (Offsite, Notifications, System, and a few stragglers the earlier Schedules-tab round had missed) to the same two shapes — including two whole-object-POST cards (CloudCard, NotifyCard) that turned out to fit the ordinary "ask does this field show a real live value" test just fine despite the different transport underneath — and is the round that actually forced the four-exception catalog above into words, rather than leaving "earns its place" as a phrase nobody had needed to cash out yet.

## Failure feedback

Every action that can fail reports that failure through the same two channels, always both together, regardless of which control triggered it: the message goes into a toast (see "Toasts" above), never a permanent sentence left sitting on the page, and the control that was clicked plays `glim-shake` (see "The motion engine" below) once. This is the auto-save toggle's own revert-on-failure pattern above, generalized one step further — not "an optimistic value snapping back," which a plain action button has nothing of, but the shared, narrower claim underneath it: *a failed action is reported once, loudly, in the one place built for it, and the control that caused it visibly says so* — and it now covers every button on the page, not only the fields "Saving" already migrated.

Found and fixed on BombVault's Integrity tab (jdp, live review, emphatic — *"wenn Fehlermeldungen kommen sollen diese als Toast angezeigt werden. Und der Button kurz zittern. Das sollte schon als Standard in GlimStone stehen. Wenn etwas fehlschlägt soll der Toggle/Button kurz zittern. Systemweit!!"* — when an error comes back it should show as a toast, and the button should briefly shake; that should already be a GlimStone standard; whenever anything fails the toggle/button should briefly shake, system-wide): a "Verify"/"Unlock"/"Prune" row of plain action buttons (no optimistic value to revert at all — a click just calls an endpoint and reports what happened) left the raw backend error sitting on the page as a permanent inline sentence next to the button, and a second, worse copy of the same anti-pattern below it as a running list of every action's own failure text, both surviving until the NEXT click overwrote them. Neither had ever gone through the toast system already used elsewhere in the same app, and neither button shook.

- **The permanent inline sentence is removed outright, not duplicated alongside the toast.** Once the toast carries the message, a second, page-resident copy of the identical text is pure clutter with a worse property than merely being redundant: unlike a toast, it never clears itself, so a stale failure from an hour ago silently looks exactly as current as one from a second ago until something else overwrites it.
- **A minimal residual indicator, if the row still wants ANY at-a-glance mark, matches its own success indicator's visual weight — a short fixed glyph ("✗ Failed"), never the raw backend string.** A row that shows "✓ Healthy" on success and then a full, possibly-long server error on failure is showing two different WEIGHTS of information for two outcomes of the same action; the fix is symmetry, not deletion — keep a same-size fixed caption for both, and let the toast be the only place the actual, variable-length reason ever appears.
- **A genuine persistent STATUS fact is not this pattern, and stays exactly where it was.** The Integrity tab's own append-only check can return a decisive "server accepted the delete — not protected" verdict: the test ran fine and truthfully reported bad news, the same category as a red health badge, not a failed click — that verdict stays a plain inline fact with no shake and no toast. Only the OTHER branch of the same button — the test itself couldn't even run (network/server error) — is the "you clicked it, it didn't work" case this section covers. Telling the two apart is a per-control judgment call, not a mechanical one: does a fresh click of the SAME button, if it succeeded, replace this exact message with a different one? A verdict is replaced by another verdict either way (protected or not); a "couldn't run" error is replaced by success or by an equally one-shot different failure. The former stays put; the latter is this section's toast+shake.
- **A plain `<button>` shakes exactly like a `Toggle` does — the same class, the same nonce-keying discipline, no new mechanism.** `glim-shake` was never toggle-specific (see "The motion engine" below for the full "reach for it anywhere…" list, which already named a rejected form submission and a snapped-back drag) — a bare action button reads its own `shake` counter, bumps it in every catch/failure branch alongside the `push()` call, and keys the button's own `key` prop on it (`key={shake}`) so a fresh DOM node exists for the animation to replay against — identical to how `ToggleRow`'s `shakeNonce` prop already forces a `Toggle` remount. Two buttons that share one handler (an "Include all"/"Exclude all" pair, a "Save"/"Reset" pair) get **one nonce each**, not one nonce shared between them — otherwise a failure of the button NOT clicked shakes the wrong one.
- **A two-click "confirm" control must not un-confirm itself on the failure it's now reporting.** A destructive action gated behind "Remove" → "Confirm remove" (see "Destructive and confirmable actions" above) that resets back to "Remove" in its own failure branch defeats the shake in the same tick it fires — the confirm button is exactly what needs to visibly shake, and a button unmounting mid-render never gets the chance to play the animation the user is meant to see. Reset the confirm state only on SUCCESS; a failed attempt leaves the confirm button standing (now shaking) so the user's one already-spent confirm click isn't silently discarded for a failure that wasn't their mistake.
- **A control whose only "submit" is losing focus (`onBlur`), not a dedicated button, is a real exception to the nonce-keying mechanism above, not a case to force through it anyway.** The shake mechanism replays by giving the element a fresh `key`, which unmounts and remounts the DOM node — and unmounting a currently-FOCUSED element fires a native `blur` first. On a control whose blur handler IS the submit action, that native blur re-invokes the same submit with the same still-bad value, which can fail again, bump the nonce again, remount again, blur again — an animation-triggered retry loop. Leave shake out for this one shape (the toast alone still fires) until a non-remount replay exists (a `requestAnimationFrame` class-remove-then-readd, say) — forcing the general mechanism onto a control it structurally can't tolerate is a worse bug than the missing animation.

## The reveal eye (password/token fields)

A field holding a secret carries its show/hide control **inside the field** at the trailing edge: a bare eye that becomes a slashed eye once the value is visible.

- **A bare icon, never a badge or a second button.** The eye is furniture — a glyph the field's own trailing padding reserves room for, not a chrome button beside it. On a page inside a foreign host UI whose global `button` styling would paint any `<button>` as a filled badge, the eye is a `<span role="button" tabindex="0">` so nothing themes it. An app that owns its own CSS may use a real button — the look is identical either way: just the eye, nothing around it.
- **Neutral, never the accent.** Like the `(i)`, it means "look", not "activity".
- **It doesn't change the field's width.** The wrapper that positions the eye fills the column exactly like a plain field; a shrink-to-content wrapper makes secret fields read as narrower than every other field — the one thing the eye should *not* draw attention to. A verify/check action goes on its own line **below**, not beside it.

## Badges

Rules 11 and 13 already say a lot is a badge — every heading, everything clickable. What a badge actually *is* has four shape registers and a sizing discipline of its own.

- **Four shapes, not the shape engine's three.** Pill (`--radius-pill`, fully round) for standalone chips and count/data badges; rounded (a small fixed radius, matching `--radius-control`) for compact inline badges; square (0) mirrors the shape engine's square setting; circle (`--radius-pill` again, but width locked to height) for icon-only or single-glyph badges — same radius value as pill, but a distinct semantic use: a pill implies text content, a circle implies "just a glyph."
- **The raw pill token is the fix, not a cap.** `border-radius: var(--radius-pill)` (9999px in Round) already renders correctly on ANY box, square or not - the CSS corner-overflow algorithm scales all four corners down together to fit, giving a true circle on a square badge and a true stadium (flat sides, semicircular ends) on a rectangular one. `border-radius: min(var(--radius-pill), 50%)` looks like the safe cap but is actually the bug: `50%` resolves per-axis (width vs height) *before* the overflow algorithm runs, so it hard-codes two different corner radii on anything non-square and renders as a visible ellipse instead of a pill - this exact bug shipped in an adopting app's own rainbow-mode switch (a 44×24px track). Use the raw token; never the `min(…, 50%)` guard, on badges or anywhere else.
- **Sizes are named stages with one canonical source, not per-instance values.** A handful of named stages (however many an app genuinely needs — small/medium/large is usually enough) each fix a font-size, padding and height together; every badge instance reads its stage's tokens rather than repeating literals. This isn't a nice-to-have: a real regression shrunk one row's badge height in a single stylesheet while five other stylesheets styling the same row still referenced the old literal value — a 30px badge can never share a line with a 26px button next to it, no matter what alignment logic runs afterward.
- **Same stage means pixel-identical, regardless of the underlying element.** A `<button>` and a `<span>` styled to the same badge stage must resolve to the exact same rendered height — claim the full box model (`box-sizing`, an explicit `height`, `min-height: 0`, `appearance: none` on native elements) and read padding/font-size from the stage's own tokens, never from whatever that element type defaults to. Two badges built from the "same" helper function still rendered visibly different heights until this was enforced explicitly.
- **The `font-size: 0` + `vertical-align: middle` trap.** A wrapper set to `font-size: 0` (the usual fix for whitespace-node gaps between inline children) combined with `vertical-align: middle` moves the line box's strut baseline to `line-height / 2` with zero x-height, so content centers on that baseline instead of the wrapper's true middle — landing a few pixels off from a same-height sibling that still has a real font-size. Removing the `font-size: 0` while `vertical-align: middle` stays in place pushes the content back up unexpectedly in the other direction. Fix the two together, never just one.
- **The heading notch's horizontal position needs an EXPLICIT source, not an ambient one — the same "measured, never guessed" principle rule 12 already states, extended to the in-app case rule 12 doesn't cover.** Rule 20's half-overlap notch (`position: absolute`, straddling the card's own top edge via `top: 0` + a self-relative `translateY(-50%)` — never a fixed pixel offset; a percentage transform always resolves against the badge's OWN rendered height, so it re-centers correctly whether the badge is one line or has wrapped to two) sets no explicit horizontal offset either, by the same logic: with no `left`/`start` set, an absolutely positioned box falls back to its CSS *static position* — where it would have rendered had position stayed static — so it inherits whichever padding the card's own content box already uses, for free, with zero extra classes, and flips correctly under RTL for free too. That fallback is correct on exactly one shape: a single element that is BOTH the notch's positioned ancestor AND the card's padded content box, with its heading `<h2>` stretched to that box's full width. It fails *silently* — not with an error, with a badge that quietly renders in the wrong place — the moment either assumption breaks, in two different ways found independently, months apart, in the same adopting app: (1) the positioned ancestor and the padded content box are split into two different elements (needed whenever the content box is also `overflow-hidden`, e.g. to clip a progress bar's square ends to the card's own rounded corners — the notch would otherwise be clipped too if it lived inside that same box), landing the badge flush with the OUTER, unpadded box's bare edge instead of the inner box's content edge; or (2) the card is a single element but centers its own body content (an empty-state pitch: icon, text, button, all `text-center items-center`) — once the notch is the heading's only child and goes `position: absolute`, the heading has nothing left contributing to its own size, collapses to a 0×0 box, and `items-center` then CENTERS that zero-width box in the card instead of stretching it to the padding edge, landing the badge at the card's horizontal middle. Both failures have the identical symptom (badge not flush with content) and the identical root shape (the badge's position is a function of ambient DOM/CSS structure no call site ever states), which is exactly why the same bug kept recurring at different call sites across different review rounds even after being "fixed" each time — a fix that matches whichever card happens to be flush TODAY (by copying its exact div structure) reintroduces the bug the moment the surrounding markup changes for an unrelated reason. **The fix is an explicit override, not another per-instance structural patch**: a badge that needs the notch treatment (per rule 20) also accepts a plain numeric inset prop, on the SAME spacing scale as the card's own content padding (e.g. `insetStart={5}` mirroring a `p-5` box) — real CSS, resolved directly against the notch's positioned containing block, so it produces the correct result regardless of what the heading's own box collapsed to or which of the two structural recipes above the card happens to use. Pass it ONLY on a card whose recipe is provably one of the two fragile shapes above; every ordinary single-box, left-stretched Card keeps relying on the static-position fallback, which is still the right, self-maintaining answer for that shape and needs no explicit number that could itself drift out of sync with the real padding later.

## Icon glyphs

**Every icon glyph is a filled solid shape (`fill="currentColor"`), never a stroked outline (`stroke="currentColor", fill="none"`).** A line-drawn icon reads as a wireframe, sitting at a different visual weight than the filled badges, filled switches and filled active states around it (rule 3, rule 11, rule 13 — this whole language is built from *filled* shapes making a statement, not from outlines). A glyph set with some icons filled and others stroked reads as two icon libraries that happen to share a colour, not one.

- **A closed silhouette flips directly**: a padlock body, a folder, a drop, a moon crescent — anything that is already an enclosed region under a stroke just needs `stroke="none" fill="currentColor"` and the same path data; no redraw required.
- **A line glyph (an arrow, a checkmark, a plus, an X, a chevron) needs real geometry, not a thicker stroke.** A checkmark drawn as `stroke-width: 4` is still a line, just a fatter one — draw it as a filled polygon (or two overlapping filled rects for a plus/X) that occupies the same silhouette a viewer already reads as "check"/"plus"/"close". The filled variant of a well-known glyph (Material Symbols Filled, Heroicons Solid) is the reference register to match, not a stroke rendered thicker.
- **A structural detail that has to stay a thin line** (a lock's shackle, a slider's track, a clock's hands) renders as a thin *filled* shape (a filled rounded rect or a filled ring segment), never `stroke`. The rest of the glyph around it stays fully filled — the whole point is that nothing in the icon set uses the stroke render model, not that every individual stroke-like detail vanishes.
- **The info-bubble `(i)` trigger is the one deliberate, named exception** (see "The tooltip and info bubble" above: "a bare stroke-only SVG glyph, never a filled badge") — it is explanatory furniture, not a control, and a filled dot there would read as a badge announcing activity it doesn't have. Every OTHER icon in the app — nav glyphs, tab glyphs, button icons, status icons — is filled.
- **The menu/hamburger glyph is always exactly three horizontal filled bars**, evenly spaced, never a sliders/equalizer icon (two tracks with offset circular handles) standing in for it — the two read as different controls to anyone who has seen either convention before, and a settings-panel opener wearing the "adjust a value" glyph is a small, avoidable lie.

## Toasts

`.glim-toast`/`glim-toast-in` (in `reference/tokens.css`) is the CSS half; the other half is behavioral and framework-specific, so it's spec here rather than a copyable file.

- **A fixed duration, not "until dismissed."** 4 seconds is long enough to read, short enough not to pile up — a toast is a notice, not a to-do list.
- **Stacked, not replaced.** Multiple toasts queue in a fixed corner rather than one overwriting the next; each is independently dismissible.
- **Hover or focus pauses the countdown — and preserves the remaining time**, rather than restarting it. Resetting to the full duration on every hover means a toast under a wandering cursor never actually expires.
- **A "quiet" mode filters by severity, not by muting everything.** Failures and anything that blocks progress (a captcha waiting for input, an account that just got benched) always surface; routine completions can be suppressed for someone who's turned the volume down. The two categories that already have a dedicated, persistent surface elsewhere (a captcha panel, an account-health strip) skip the toast entirely rather than duplicating the notice in two places at once — a toast is for something that has no other place to live.

## Empty states

A list, table or panel with nothing in it gets a **deliberate empty state**, not blank space: a `.glim-card`, a muted icon at reduced opacity, a muted title, an optional one-line hint, an optional action button (e.g. "Add one"). The same shape serves two related but distinct situations — genuinely nothing exists yet, versus a filter/search matched nothing — with different copy for each; conflating them ("No results" when the real answer is "you haven't added anything yet") sends the user looking for a filter to clear that was never set. A spot where the shared empty-state shape genuinely doesn't fit is fine as a one-off exception — document *why* inline where it happens, so it reads as a deliberate call and not an overlooked gap.

## The version footer

An app's build version (and the GlimStone version it's built against) belongs in Settings, not under the logo in the nav rail — the rail is for orientation, not diagnostics, and a version string competing with the app's own name for that one line of space loses the name its own weight. It lives instead as a single quiet line, **fixed to the corner of the actual browser window** (not the settings content's own scroll container), so it reads on every settings tab without being implemented per tab and without competing with anything else pinned to the bottom of that scroll area (an unsaved-changes bar, say) for the same sticky slot — the two are positionally independent by construction. `pointer-events-none` and a low-opacity muted tone (`text-carbon-textMuted/50` at `10px`, tabular numerals) keep it a background fact rather than a control: legible on demand, invisible the rest of the time. First built for KnightLoader (`web/src/pages/Settings.tsx`'s `VersionFooter`), after the same information had first been tried as a single card on one settings tab and found to only ever be seen by someone who happened to open that specific tab.

## Destructive and confirmable actions

Not every removal deserves the same friction, and treating them identically is itself the bug.

- **Reversible actions don't ask.** Dropping a row from a working list (re-addable in one step) fires immediately — a confirmation dialog in front of an undoable action just teaches people to click through confirmations without reading them.
- **Irreversible actions get a real confirmation that states the stakes**, not a generic "Are you sure?" — the exact count and, where it applies, the size of what's about to be gone. It's the standard `.glim-card` window (rule 15), not a native browser dialog: a native `confirm()` can't be styled, can't be localized consistently with the rest of the UI, and blocks the entire tab while it's open.
- **The destructive control is always the fault colour.** Not the accent, never a neutral grey "Delete" sitting next to neutral "Cancel" — the one control on the screen that ends something permanently is the one place status-red belongs on a button.

## Charts (provisional — extracted from a single example, revisit once a second chart exists)

- **Hand-drawn SVG, not a charting library.** A smoothed line path, filled underneath with an accent-colour gradient fading to transparent, stroked in the accent at a hairline weight.
- **One colour source: the accent, never rainbow or status hues.** A chart shows a quantity over time, not a set of distinct identities — the plural colour modes exist for the latter.
- **No axes, no gridlines, no tick labels.** A single eyebrow-style caption states the current or peak value in words; the shape of the line is the point, not a coordinate system to read precisely.
- **The live edge pulses** (`.glim-live`), same treatment as any other "this is happening now" indicator elsewhere in the system — a chart isn't a special case, it's rule 4's accent-means-running applied to a curve instead of a badge.
- **Idle degrades to a flat, muted hairline — not a gold line sitting at zero.** The accent means activity; a coloured line with nothing happening behind it is the same mistake rule 3 already rules out elsewhere, just easier to miss on a chart.

## Inside a foreign host UI (Unraid plugins)

A plugin page inherits the host's global form and button CSS. Two things that have cost real time:

- **Specificity beats a single class.** Unraid's `button[type=button]:where(…)` (0,1,1) beats `.my-btn` (0,1,0) — the button gets the host's ghost styling (transparent, accent text, gradient border). Component rules should therefore be **prefixed with the app's root class** (`.app-cfg .app-btn` = 0,2,0), the same way input rules already have to be. Icons (the eye, the `(i)`) stay `<span>`, never `<button>`, so no button chrome applies; a hidden toggle checkbox needs `position: absolute !important` hard-pulled out of flow, or a host reset shoves it back and the pill drifts.
- **Native by default, GlimStone only with the companion app installed** (one markup base, two looks). Without that companion, the page should look **fully native to the host** — style layout only, lean on the host's own form CSS (underlined inputs, native checkbox toggles, the host's own type). The GlimStone look (cards, wells, eyebrows, pill tabs/toggles, filled chips) lives in a **second layer**, gated behind a class the companion app stamps onto `<html>` when it's present, with higher specificity, reading the shared tokens only then. GlimStone is **progressive enhancement, not the default.** The anti-pattern seen in the wild: GlimStone applied unconditionally with token fallbacks baked in — the page then stands there as "GlimStone in the host's own orange" when the companion app isn't installed, and doesn't read as native to anyone.

## The user-owned axes

Theme, shape, accent and language are all settings, and every one of them is **applied once at the app root** — never by the page that edits it. A settings page reads the current value and writes the new one; it never carries the styling logic itself, or two pages would be free to disagree about how "square" looks.

Two of these axes hand off to a named **engine** — a single mechanism that turns one input (or, for colour, three) into every token a component reads, so nothing downstream has to know which setting produced the value it got. Shape has one: the **shape engine**, below. Theme, accent and rainbow share one: the **colour engine**, below that. Language doesn't — it changes structure (`lang`, `dir`, which glyphs get requested) rather than resolving to a token set, so it stays "an axis" and not "an engine."

- **Theme** sets `data-theme` on `<html>`: `light` · `dark` · unset, which follows the OS via `prefers-color-scheme`. **Default is system**, not a hard-coded light or dark — an app that opens dark on a light-mode OS made a choice nobody asked it to make. A user who picks light or dark explicitly overrides the OS until they clear it.
- **Shape** sets `data-shape` on `<html>`: `round` (16/10px) · `soft` (8/5px) · `square` (0). **One** token drives every radius, no exception list — this is the whole shape engine; there is no further mechanism beyond the three token sets in `reference/tokens.css`.
  - **A new component is wired into both engines AS it's built, not audited in afterward.** Adopting `--radius-control`/`--radius-pill`/`--accent` isn't automatic just because the tokens exist in the file — a new control still has to actually point its own CSS at them instead of a plausible-looking hardcoded value, and that step is easy to skip precisely because a hardcoded `rounded-full` and a shape-engine-correct `rounded-pill` render IDENTICALLY at the default (round) setting — the gap only becomes visible once someone actually switches to square, which a quick build-and-glance rarely does. Found in production, more than once, in small, low-visibility controls (a dismiss "×", a quick-fill button, a handful of ad-hoc status chips) rather than in whole new components: whoever wrote each one reached for a familiar Tailwind class instead of checking how the nearest sibling control of the same kind was already styled. The rule that actually catches this: before hand-writing any radius or accent-colour value on a new control, grep for how that same KIND of control (another dismiss button, another status chip) is already styled elsewhere in the app, and copy the token, not just the general shape — then verify by actually toggling shape/accent/rainbow and watching the new control respond, not by reading its class list and assuming.
- **Accent** overrides `--accent`; `--accent-contrast` is **computed** from sRGB luminance, never asked for as a second setting — asking for a second colour just to make the first one legible is a trap, not a preference. **The default, before anyone has touched the setting, is Sunflower gold `#FCC419`** (`DEFAULT_ACCENT` in `reference/appearance.ts`) — a fresh install of any app that shares this language opens in the same colour, so the family reads as one product from the very first screen, not just after someone finds the picker.
  - **The custom colour control opens a floating picker popover, never a native `<input type="color">`.** A native colour input hands off to a browser/OS surface entirely outside the page — on many setups a genuinely separate top-level window, not an inline popover — which is exactly what this rule exists to rule out (jdp, building CannonadeCommand: *"ich will das Farbwählfeld fest integriert"* — I want the colour field permanently embedded; the same rejection recurred nearly verbatim in an adopting app that tried the native-input shortcut anyway: *"es soll sich kein komplett neues Fenster öffnen"*). It's also functionally unverifiable in automated testing — a native picker's surface sits outside the page's own DOM, so nothing can prove it opens, let alone opens correctly. Use `reference/colorPicker.ts`'s `openColorPickerPopover(trigger, hex, onChange)`: a real saturation/value square + hue bar (`.glim-picker`/`.glim-picker-sv`/`.glim-picker-hue`), drawn in the app's own DOM inside a floating `.glim-picker-popover` anchored to the trigger that opened it, closing on outside click, Escape, scroll or resize. The bare `colorPicker()` (permanently embedded, no popover) is still available for a page with genuinely dedicated, permanent space for exactly one control — CannonadeCommand's own settings PAGE, which has room to spare — but a *popover* is the default for a compact settings CARD, where embedding the picker permanently grows the card every time one is added (the same jdp who wanted CC's picker "fest integriert" wanted TrickWork's own card-based picker floating instead, once the always-embedded version visibly bloated the card — same underlying preference, "no separate OS window", satisfied either way).
  - **Every custom colour value — whether it's the app's one accent or one of a palette's several positions — gets the SAME trigger: a flat colour swatch, same size and shape as the preset swatches beside it.** Clicking it opens the shared popover anchored to that swatch, pre-synced to its current value; only ONE popover is ever open across the whole app (`openColorPickerPopover` closes any previous one automatically). This unifies what used to be two different layouts (a single value shown permanently, a multi-value palette revealed-on-click) into one: a popover has no "permanently visible" state to begin with, so a single custom colour and one palette position are handled identically.
  - **Preset/palette swatches stay flat colour circles, not pickers of their own.** Each is a plain filled circle (`background-color` set from its own hex, `border-radius: var(--radius-pill)`, a border-colour highlight on whichever is active — rule: "Voreingestellten Farben gekennzeichnet wie in BombVault") that a click selects; the custom-colour trigger is one more circle in that same row. A reset control is a **badge with an icon** (a counter-clockwise arrow), not a text link — see rule 13 — pinned to the row's trailing edge with `margin-inline-start: auto`.
  - **Swatches follow the shape engine.** `border-radius: var(--radius-pill)` on each preset — Round keeps them circular, Soft/Square progressively square them off, the same way any other shape-reactive control does. This isn't automatic just from adopting the shared token: an app has to actually point its own swatch CSS at `--radius-pill` rather than a hard-coded `50%`. The picker's own SV square and hue bar read `--radius-control`/`--radius-pill` respectively (a real 2D field, not a badge, so it takes the rectangular-control register).
- **Language** sets `lang` (and `dir`, see below) on `<html>`. Default is the browser's own locale (`navigator.language`) if it's supported, English otherwise — never a hard-coded language shown to everyone regardless of their system. The picker itself is a plain `<select>` (rule 14), not the horizontal selector above: a language list runs to dozens of entries, and a control built for "everything visible at once" stops working once it has to wrap or scroll.
  - **Each option carries its flag as an emoji prefix** (`🇬🇧 English`, `🇩🇪 Deutsch`), not a background-image/sprite flag icon library. A native `<option>` can only ever hold plain text — no image, no CSS background — so a "real" flag icon (an SVG sprite, a `flag-icons`-style CSS class) forces a custom-built dropdown to render it at all, which is exactly the `<select>` this rule just ruled out for a 26-entry list. The regional-indicator emoji sequence (two Unicode codepoints per ISO 3166-1 alpha-2 code, e.g. `GB` → `🇬` + `🇧`) needs nothing beyond string concatenation — `reference/flagEmoji.ts`. The closed select's own displayed text already shows the selected option's flag for free, since it's just that option's text.
  - **Windows renders the same codepoints as a compact two-letter tag, not a pictorial flag** (`GB` in a small coloured badge rather than a Union Jack) — a deliberate, long-standing Microsoft policy in its emoji font, not a rendering bug, and true of every Windows application, not just a browser quirk. macOS, Linux, iOS and Android all show the actual flag glyph from the same two codepoints. This is still a strict improvement over no flag at all (the two-letter tag is legible, coloured, and distinguishes entries at a glance), just not pictorial everywhere — know this going in rather than filing it as broken the first time it's checked on Windows.
  - This is the plain-`<select>`-compatible **default**, not a mandate: a native select's own closed-field height and its browser-owned open-list row padding are both effectively unstyleable, and a language list is exactly where that stops being cosmetic — an adopting app (framework or not) that finds its own field or list reading as cramped even after reasonable padding should build a custom button+listbox dropdown instead (the browser-column trigger + absolutely-positioned listbox pattern, opening toward whichever edge of the viewport has room), carrying the same flag-emoji-prefixed option text. This isn't gated on already using a component framework for other reasons — a framework-free app hits the same native-select ceiling and gets to reach for the same fix.
  - **An app that already took that custom-listbox step can go one further and fix Windows' own flag rendering, not just work around it.** A native `<select>`'s open popup is drawn by the OS itself on Windows regardless of page CSS, so no webfont reaches it — but a custom listbox is real page DOM, so a scoped `font-family` on just the flag span *can* override which glyph gets requested. The [`noto-color-emoji-flags`](https://www.npmjs.com/package/noto-color-emoji-flags) package (OFL-1.1, a ~800KB COLR-vector subset of Google's own Noto Color Emoji containing only flag glyphs — not Twemoji, which is CC-BY and fails the OFL-only asset rule) is a drop-in fix: `@import 'noto-color-emoji-flags';` in the app's stylesheet, then `font-family: 'Noto Color Emoji Flags', <the rest of the app's normal text-font stack>;` on the flag span only (never the whole page — the rest of the UI should keep using its own text font). Real pictorial flags on Windows too, same as macOS/Linux always had.
- **Motion intensity** sets `data-motion` on `<html>`: `off` · `subtle` · `full`. **Default is full** — the richest experience, since this axis is additive polish a user dials DOWN, not a compatibility fallback a user has to opt INTO (contrast Theme's "system" default above, which exists because nothing else in the stack already reads `prefers-color-scheme` unconditionally — `prefers-reduced-motion`, by contrast, IS already read unconditionally by the motion engine below, so a "system" option here would just re-derive a signal the app honours everywhere already, for a control whose entire reason to exist is letting a user WITHOUT OS-level reduced motion still dial intensity as a style preference).
  - **A deliberate reversal, not a bug fix.** "The motion engine" section below still reads, verbatim: *"This is the accessibility signal, not a GlimStone setting (see 'the axes we don't have' above): no in-app toggle duplicates it today."* That was the considered call as of 2026-08-18 — motion intensity was accessibility's job, not a style preference's. jdp reversed it explicitly rather than an implementer quietly reintroducing what had been ruled out: *"Wäre eine Animationsengine gut?"* → *"Echte Engine mit eigenem Nutzer-Schalter"* (a real engine, with its own user-facing switch). The old sentence stays in place below as the historical record of what was decided and why at the time — this bullet is what superseded it, not a correction pretending the old call was wrong.
  - **Composes with, never overrides, `prefers-reduced-motion`.** The OS signal stays exactly what it was: unconditional, and it still wins. `data-motion`'s three states only ever resolve INSIDE the existing `@media (prefers-reduced-motion: no-preference)` block — the `(reduce)` block keeps its own hard-coded fallback values completely untouched and unconditional, so a browser reporting OS-level reduced motion never even reaches a `data-motion` selector for these properties; it simply never evaluates them. A user who manually picks "off" without OS-level reduced motion gets the SAME numbers the `(reduce)` block already uses for the same element — "off" is "the manual equivalent of what OS-level reduced motion already does," not a second, separately-tuned recipe.
  - **Mechanism, mirroring the shape engine exactly:** duration/distance/amplitude tokens (`--motion-page-dur`, `--motion-toast-slide-scale`, `--motion-shake-scale`, and siblings) redefined per `[data-motion="subtle"|"off"]`, consumed by the SAME keyframes at every intensity — "subtle" and "off" are smaller numbers, not forked animations, the identical "one token set, no exception list" shape the shape engine's own radius tokens already use above.
  - **The first adopting app's port covers four of the five reference keyframes, not all five, and says so rather than papering over it.** BombVault (the first app to build this axis) resolves `glim-page-in` (locally renamed `bv-page-in`), `glim-toast-in`, `glim-fade-in` and `glim-shake` through the new tokens; `glim-pulse` (the `.glim-live` "this is happening now" indicator dot, below) has never been adopted in that app at all, so there is nothing of that name to retrofit there yet. `glim-shake`'s own "off" state needed more than a zero-amplitude shake — an invisible shake carries no "rejected" signal — so it swaps to BombVault's own pre-existing `bv-egg-fade-pulse` (a local keyframe already serving as `glim-shake`'s `prefers-reduced-motion` substitute, unrelated to and predating this axis) rather than to the reference's `glim-pulse`, which that app doesn't have. An app that HAS adopted `.glim-live`/`glim-pulse` should give it the same off/subtle/full ladder as the other four when it adopts this axis — not leave the one infinite animation as the one thing the new setting can't touch.
  - **Persistence:** localStorage-only (`bv-motion` in BombVault, mirroring `bv-shape`), applied once at the app root via an `applyStoredMotionIntensity()` call at boot — the same "single-operator tool, no second viewer who needs to agree on the current setting" reasoning Shape and Accent already give above for staying client-side rather than a server round-trip.

**On engines we don't have.** Chromium, Gecko and WebKit differences (clipboard permissions, native widget chrome, form-control quirks) are real, but they live in *application* code, not here — every axis above resolves through standard CSS custom properties and media queries (`prefers-color-scheme`, `prefers-reduced-motion`, logical properties), which behave identically across engines. A "browser engine" would only earn a place here if GlimStone itself ever needed to branch its own *visual* rules by engine; nothing in this document currently does.

## Right-to-left languages

Setting `dir="rtl"` on `<html>` (Arabic, Hebrew) mirrors layout through the Bidi algorithm, and most of the system holds up under it for free — the token-driven spacing and alignment already use logical properties (`margin-inline-start`, not `margin-left`), so a card, a form field or a section badge just flips. Two things don't get to flip automatically:

- **Technical content stays pinned left-to-right.** A path, URL, filename, API key or log line is not language — it's data, and the Bidi algorithm reorders neutral characters (`/`, `.`, `-`) inside it as if it were prose. `/data/downloads` under `dir="rtl"` renders as `data/downloads/`: still the same string, but visually a different path, and a user reading it will believe their files live somewhere else. Any field or display showing technical content gets `dir="ltr"` **and** `text-align: start` (so its *position* still follows the surrounding RTL layout — only the text *inside* it stays LTR).
- **Directional icons mirror, symmetric ones don't.** An arrow, a chevron, a "forward" glyph that implies a reading direction gets mirrored under `dir="rtl"` (`transform: scaleX(-1)`, or a dedicated RTL glyph if mirroring distorts it). An icon with no inherent direction — a gear, a trash can, the reveal eye — never does; mirroring it just makes it look subtly wrong for no reason anyone can name.

Verify RTL on the rendered page, not by reading the CSS: a logical property used correctly and one used incorrectly look identical in the source and only differ once the browser actually flips the layout.

## Non-Latin scripts

The font stack ends in `system-ui, sans-serif`, not a fixed list of named fonts, and that's deliberate: a browser missing a glyph in the first-choice font (Segoe UI's CJK coverage is thin) falls back **per character** to whatever the OS already has installed for that script — it does not need every script's font to be listed by name to render correctly. Two things that font stack alone doesn't cover:

- **Letter-spacing is a Latin assumption.** The base `-0.008em` tightening reads as normal kerning on Latin letterforms and as crowding on CJK, which is set in full-width square cells that don't kern the same way. Scope it out for CJK content: `:lang(ja), :lang(zh), :lang(ko) { letter-spacing: normal; }`.
- **`.glim-num`'s tabular figures are a Latin-digit feature.** `font-variant-numeric: tabular-nums` only affects the Western Arabic numerals (0–9) most fonts ship as monospaced-width by convention; it has no defined effect on native digit systems (Eastern Arabic-Indic, Devanagari) some locales display instead. Where a locale's own digits are shown, column alignment has to come from a fixed-width container instead of the numeral feature.

## The colour engine

Theme, accent and rainbow are three inputs into one mechanism, not three separate systems: **theme** picks which half of the palette (`:root` vs `[data-theme="light"]`) is active, **accent** overrides the activity hue on top of it, **rainbow** multiplies that hue by list position. All three ultimately resolve to the same handful of tokens — `--accent`, `--accent-contrast`, `--accent-soft`, and whichever `--carbon-*` step theme selected — so a component reading `var(--accent)` never needs to know which of the three produced the value.

The four state hues (rule 4) are the one thing that never runs through this engine: settled/fault/warning/neutral are fixed per theme, not user-editable, and never rainbowed — green has to mean "finished" everywhere, unconditionally.

### Rainbow — the accent, plural

Eight colours handed out by **position** instead of one colour everywhere. Three sub-switches:

| Switch | Meaning |
|---|---|
| `rainbow` | master |
| `rainbowReactive` | rests neutral, colour on hover + on whatever is active |
| `rainbowRotate` + `rainbowSeed` | offsets the starting colour; **the seed lives on the instance**, not the browser — two clients of the same server must never disagree about a download's colour |
| `rainbowPalette` | all eight editable; taken **only as a complete set** |

**Mechanism:** an element that owns a position sets `--item-hue` (`hueVars`) and carries `.glim-hue`; the stylesheet redefines `--accent` **for that subtree**. Every component that already paints activity picks the colour up automatically — none of them has to know the mode exists. `.glim-tint` washes the whole element at 16% (as an inset shadow, so the row's own hover tint still shows through); `.glim-tint-badge` is the same mechanism at a stronger 50%, for a compact circular badge that needs colour AT REST (a badge with no active/checked state of its own to fall back on, e.g. a genuine multi-way picker rendered as separate badges rather than one horizontal selector); `.glim-tint-hover` is the same wash but rest-quiet, revealed only on hover/focus (below). `.glim-hue-icon` additionally colours a glyph — situational, see the icon-only badge bullet next, not a default pairing. The set's active/selected member additionally carries **`.glim-active`** (the shared marker class, not just whatever app-specific "this one is selected" class already exists alongside it) — `.glim-tint.glim-active` reads the stronger 22% soft tint instead of the plain wash, so the selected row still reads as distinct from its neighbours instead of collapsing into the same flat colour as everything else in the list.

**An icon-only TOGGLE badge (a real checked/unchecked state of its own) carries ONLY `.glim-hue`, unconditionally — no tint class at all.** Two rounds in a row tried washing the idle badge's background - first the plain `.glim-tint`, then the stronger `.glim-tint-badge` once the first read as too faint - and a real adopting app rejected BOTH ("die iconbadges sollen nicht eingefärbt sein und erst wenn man sie klickt. diese halb abgedunkelt eingefärbt sein gefällt mir nicht" - the badges shouldn't be coloured at all until clicked; this half-darkened-looking wash at rest isn't wanted). The correct behaviour was already sitting there unused: `.glim-hue` redefines `--accent` for the subtree, and the component's OWN checked-state CSS (`.icon-toggle-button--active { background-color: var(--accent) }`) already reads it - so at rest, where nothing references `--accent`, NOTHING shows, and once checked, the badge fills solid with its position colour. `.glim-hue` still has to be unconditional (not just added while checked) for that fill to resolve correctly the moment it's needed. The glyph itself stays `currentColor`/neutral either way (an even earlier revision recoloured it too via `.glim-hue-icon` and that was rejected first: "die icons sollen nicht eingefärbt werden, nur die badges also der hintergrund"). `.glim-tint-badge` is still real and still useful - just not for a TOGGLE, which already has its own fill; reach for it on a badge with no checked state of its own that still needs to show colour at rest.

**A badge with no persisted state at all doesn't own a rainbow position, full stop.** A momentary action (undo, redo, zoom in/out - nothing to check or select, just something that happens once and is over) has no "clicked and stays that way" moment for `.glim-hue` to attach a fill to, unlike a real toggle. Wiring it into rainbow anyway means reaching for a wash class to manufacture a rest-state colour that isn't backed by anything - exactly the pattern the toggle bullet above just ruled out. Same exclusion family as a horizontal selector's inactive segments (below): not everything on the page is a member of a coloured set.

**A row of equal-weight ACTIONS (not a persistent selection) reads as noisy fully washed at rest, even under plain `on`.** Export-format buttons, say: none of them is "selected," they're just always-available choices, so four buttons permanently lit up in four different colours competes with the page instead of accenting it. `.glim-tint-hover` gives that ROW rest-quiet/hover-reveals behaviour on its own, independent of whether the user's global setting is `on` or `reactive` (jdp: "die buttons die inaktiv sind sollen nicht eingefärbt sein, beim mouseover sollen sie eingefärbt werden") — the app isn't asking the user to opt into reactive mode globally just to quiet one row down. Use `.glim-tint` where colour-at-rest IS the point (a list — an all-idle list needs to show something); reach for `.glim-tint-hover` where it's a nice-to-discover accent on a row of otherwise-equal actions.

**Five traps, all hit in production:**

- **Position, not an id hash.** A hash keeps a row's colour as rows above it finish — sounds better, until three rows land in the same bucket and two neighbours share a colour. Position is exactly what the mode exists to prevent.
- **The row needs the wash.** Without it, colour only reaches the row through the progress fill — and that turns green on completion (rule 4). On a list of finished downloads, the one mode built for lists showed nothing at all.
- **The wash alone is not enough, and the active row needs its own class.** The original 7% wash figure shipped in 1.0.0 tested fine in isolation but drew three independent "the mode does nothing when I turn it on" reports from a real adopting app before anyone thought to measure the actual rendered colour rather than eyeball it — it was applying correctly the whole time, just under the threshold anyone registers as change. Raised to 16% (selected: 22%). Separately, and worse: `.glim-tint`'s own box-shadow declaration has higher specificity than a typical single-class `.active`-style app rule, so it silently won the cascade against an app's own active-row highlight in every adopting app that never carried the shared `.glim-active` class — the active row looked exactly like every other row, in `on` mode as well as `reactive` (the fix in 1.4.0 was scoped to `reactive` only at first, since that was the only mode the original bug report happened to demonstrate against — always check whether a fix generalises to sibling modes, not just the one that was tested).
- **Tailwind's `@theme` resolves once, at `:root`.** `--color-accent: var(--accent)` inside `@theme` gets evaluated at `:root` and frozen there — every utility generated from it (`bg-accent`, `text-accent`) points at the global accent forever, and a `.glim-hue` subtree that redefines `--accent` never reaches it. Rainbow coloured everything that read `var(--accent)` directly and nothing that went through a utility class. The hue rules have to set `--color-accent`, `--color-accentContrast` and `--color-accentSoft` **themselves**.
- **Wiring ONE set is not the same as wiring the mode.** An adopting app that hooks rainbow up to only its most obvious list (a download queue, say) has implemented a feature that colours one part of the screen, not "rainbow mode" — and a user comparing it against a sibling app where the whole surface goes rainbow-lit (badges, segmented-control segments, icon toggles, every equal-member set) will keep reporting "it doesn't apply" no matter how many times the one wired set is fixed, because their own bar for "applied" was never that one list. `rainbowColor(i)`/`hueVars()` are already general-purpose — nothing about them is queue-specific — so the fix is coverage, not new mechanism: walk every genuine equal-member set in the app (rule: "anything that is the only one of its kind on the page keeps the single accent" is the ONLY exclusion) and wire each one, not just the first one that looked like an obvious fit. `.glim-hue` still needs to sit on an icon-only badge UNCONDITIONALLY, not just while checked/active, for the checked-state fill to resolve `--accent` correctly — see the icon-badge bullet above for which OTHER class it pairs with (and which one it doesn't, any more).

**Security:** every palette colour lands in a CSS custom property. Validate server-side with `^#[0-9a-fA-F]{6}$`, and take it **all-or-nothing** — seven good colours plus one injected value isn't an 87%-safe palette, it's an invisible line.

## The motion engine

Five keyframes cover everything that moves: `glim-page-in` (a page or section settling in, 280ms), `glim-toast-in` (a notification sliding in, 220ms), `glim-fade-in` (the info bubble and other transient UI, 110ms), `glim-pulse` (the `.glim-live` dot, 2s, infinite), `glim-shake` (a control refusing an action, 360ms, one-shot). All five exist to answer one question — is this new, arriving, ongoing, or refused — and nothing else in the system animates: a settled page doesn't idle-animate, a card doesn't breathe, hover states change instantly.

- **Fast by default, and faster the closer it is to input.** Entrances that follow user intent (opening a page) get the full 280ms with an ease-out curve; something the pointer is already waiting on (the info bubble) gets 110ms flat — a bubble that fades in slowly reads as *lag*, not as *polish*, because the cursor got there first.
- **`prefers-reduced-motion: reduce` swaps entrances for a plain fade, never nothing.** `glim-page-in`/`glim-toast-in` drop their translate and shrink to a 160–180ms opacity-only fade under the media query — an element still needs to *arrive* legibly, just without the motion component. This is the accessibility signal, not a GlimStone setting (see "the axes we don't have" above): no in-app toggle duplicates it today. **Reversed 2026-08-23** — that last sentence was true when written and is kept here as the historical record, but it no longer describes current policy: see **Motion intensity** under "The user-owned axes" above for the manual `data-motion` axis jdp asked for after all, and why an accessibility signal and a style preference turned out to be two different things worth two different controls.
- **An infinite animation gets a true stop under reduced motion, not a slower version.** `.glim-live`'s pulse communicates "this is happening now" — under `prefers-reduced-motion` it renders as a static, fully-opaque dot instead: `.glim-live { animation: none; opacity: 1; }`. A continuous animation is exactly the category `prefers-reduced-motion` exists for (unlike a one-shot 110–280ms entrance), and "this item is live" still has to read from its colour and position alone once the pulse is gone.
- **This is independent of the colour engine's reactive mode.** Rule 10 exists because of a real regression: reactive rainbow (colour rests neutral, appears on hover) was once implemented by also suppressing nearby animation, which silently turned `.glim-live` off for anyone running reactive. Colour mode and motion are two different engines reading two different signals (a setting vs. an OS preference); neither one gets to reach into the other.
- **A control that can't do what it was just asked shakes instead of just silently reverting.** A toggle switched on, then refused by the backend (a real precondition the UI can't check in advance — no SSH connection configured for a feature that needs it, say) needs to visibly communicate "that didn't work," not just quietly snap back to its previous state while the real explanation sits in a toast the eye may not be on yet. `glim-shake` is a 360ms `ease-in-out` `translateX` oscillation — `0%/100%: 0`, decaying `±4px → ±4px → ±2px → ±2px` through the middle four keyframes — applied to the control itself at the moment it reverts. Under `prefers-reduced-motion: reduce` it swaps for a brief opacity pulse (the same "arrive legibly without the motion component" substitution every other entrance gets), never nothing. **Replay on a repeated identical failure needs a fresh DOM node, not a re-toggled class** — an animation already at rest doesn't restart just because its class briefly leaves and returns in the same frame; key the shaking element (or its animated child) on an incrementing per-instance failure counter so a second consecutive rejection of the same action visibly shakes again, exactly like `lib/toast.tsx`'s `push()` minting a fresh id per call so an identical repeated message still gets a fresh node. Genuinely reusable — name it for the gesture (`glim-shake`), not for the first control it happened to ship on (never `toggle-shake`/`domain-toggle-shake`), and reach for it anywhere a UI action is optimistically shown then has to be undone: a rejected toggle, a form field that fails server-side validation after looking locally valid, a drag that snaps back because the drop target refused it. It reaches further than "something to undo," too: see "Failure feedback" above for the same animation, paired with the same toast, on a plain action button that never had an optimistic value to revert in the first place — a "Verify"/"Delete"/"Save" click that just calls an endpoint and reports what happened.

**Round 2 — seven more animations, plugged into `data-motion` from the start.** BombVault's own second pass at this axis (see "Motion intensity" above for the engine itself) didn't stop at retrofitting the five keyframes that already existed — it added seven new ones, each reading the SAME off/subtle/full tokens and resolving inside the SAME `@media (prefers-reduced-motion: no-preference)` gate as a starting requirement, not a follow-up. Each is named for the gesture, not the first control it shipped on, same convention as `glim-shake`.

- **Shape-morph.** Changing round/soft/square in the Shape picker transitions every `--radius-card`/`-control`/`-pill`-driven corner instead of snapping. `transition: border-radius <dur> <ease>` on the shape-reactive utility classes, `<dur>` off/subtle/full at 0/140/260ms. **Scoped to AFTER mount, deliberately**, not just relying on a transition being a no-op for a freshly-painted element's own first frame (true, but not the point being guarded against): the transition only activates once a class the app arms two animation frames after its initial render is present, so the mechanism's correctness doesn't quietly depend on timing coincidences a future change could break. Reduced motion: the transition property itself lives inside the `no-preference` gate, so OS-level reduced motion sees an instant snap, the same as "off."
- **Confirmation-pulse.** `glim-shake`'s gentler sibling for the opposite outcome — a field or toggle that just auto-saved successfully gets a brief glow (`box-shadow` ring, 0→6px→0 spread) plus a small scale pop (1 → 1.05 → 1), layered on top of whatever toast already reports success, never replacing it. Reads `--accent-soft` for the glow colour, so a row that owns a rainbow position pulses in ITS OWN hue for free — the same `[data-rainbow] .glim-hue` subtree redefinition every other hued control already rides on, no separate rainbow-awareness needed in the pulse's own rule. Off/subtle/full scale the glow spread and scale delta by 0/.5/1 and the duration 0/260/420ms. Same fresh-DOM-node replay mechanism as `glim-shake` (a per-field success counter, not a re-toggled class) — the two are genuinely mutually exclusive in practice (a save either fails or succeeds) but share one combined key so an app can't accidentally freeze one counter's remount by only reading the other.
- **Staggered list fade-in.** Same-type rows (a container list, a peer list) fade/slide in with a small per-row delay instead of all appearing at once — `animation-delay: min(row-index * step, cap)`, the `min()` doing the capping in one declaration rather than a JS clamp. Off/subtle/full: step 0/15/30ms, cap 0/200/480ms, so even a 50+ row list finishes its own stagger within half a second at full richness and instantly at off. Reuses whatever per-row list-position index the app's OWN colour engine already threads through for rainbow mode — a second counter would drift from the first the first time someone edited one without the other.
- **Colour-wipe.** Flipping rainbow mode on/off/reactive wipes every hued element's colour over a fixed window instead of every one snapping independently. A temporary class toggled onto the root for ~500ms around a genuine mode change (never on boot, never on a no-op re-apply of the same resolved state) carries `transition: background-color, color, border-color, box-shadow, fill, stroke <dur> <ease>` — `<dur>` 0/160/320ms off/subtle/full. **A real cascade trap, caught live, not by reading the rule:** almost every element this needs to reach is ALSO shape-reactive (a button, a badge), and `transition` is a shorthand — two same-specificity rules setting it don't merge, the higher-specificity one wins outright. At equal specificity to the shape-morph rule above, colour-wipe was silently losing its entire property list on every hued button, so the colour flip snapped instead of wiping — verified via `getComputedStyle().transitionProperty` showing only `border-radius` on a hued button mid-wipe, zero interpolated frames across ~50 sampled animation frames. Fixed by deliberately doubling the wipe rule's own class in its selector (`.wipe.wipe *`, a well-known specificity bump, not a typo) to tie and win the tie by source order. **The general lesson, not just this one collision:** any two motion-engine rules that both reach for the bare `transition` shorthand on overlapping elements are one accidental specificity tie away from one silently eating the other's entire property list — worth a live `getComputedStyle().transitionProperty` check on a genuinely double-matched element whenever a new transition-based (not keyframe-based) axis is added, not just a glance at each rule in isolation.
- **Drawn-checkmark.** A busy→success check indicator (a verify/drill/tamper-test result, a settings-import confirmation) draws itself via SVG `stroke-dashoffset` instead of appearing whole. `pathLength="1"` on the `<path>` makes a plain `1 → 0` dashoffset always draw the entire glyph regardless of real path geometry — no `getTotalLength()` math needed. Off/subtle/full duration: 0/200/360ms. **The safe default lives OUTSIDE the reduced-motion gate, not inside it, and that ordering matters:** the unconditional base rule is "fully drawn, no animation" (`stroke-dashoffset: 0`); the `no-preference` block OVERRIDES that to start undrawn and animate back. Write it the other way — animated version as the base, reduced-motion override forcing it drawn — and a browser or a future edit that fails to load the override leaves the checkmark permanently invisible instead of merely un-animated. Stroke colour is `currentColor`, never a rainbow hue: a success/fail glyph is a state colour (rule 4's territory), not a list-position identity.
- **Skeleton-to-content crossfade.** Whatever replaces a loading placeholder once data arrives fades in (`opacity 0 → 1`) instead of snapping into place. Off/subtle/full: 0/120/220ms. Deliberately the SIMPLEST of the seven — an entrance-only fade on the freshly-created content node, not a true two-layer overlapping crossfade (the placeholder and the real content are two different conditionally-rendered elements that are never both on screen at once in a normal document flow, so there is nothing to overlap without adding absolute-positioning stacking that this specific gap didn't call for). Plays once per real mount, same "a persistent class on a freshly-created node only plays its entrance once" mechanism as `glim-page-in`/`glim-toast-in` above — a background refresh that keeps the same rows mounted never replays it.
- **Directional panel slide.** Switching between horizontally-arranged sections (a tab strip) slides the new panel in from the trailing edge when moving to a LATER section, from the leading edge when moving to an EARLIER one — `translateX(dir * dist)` where `dir` is computed by the tab strip's own click handler (it has both the old and new position in the same synchronous event, the one place that's still true) before the panel remounts. RTL-aware the same way the toast entrance's own slide distance already is: a `--dir-sign` token flips under `[dir="rtl"]` so "later" keeps meaning "trailing edge," not "always rightward." Off/subtle/full: distance 0/10/18px, duration 0/130/220ms.

## Tokens (the contract)

Defined under `:root` / `[data-theme="light"]`.

| Token | Role |
|---|---|
| `--carbon-bg` | page ground |
| `--carbon-sidebar` | nav rail ground (a touch deeper than the page) |
| `--carbon-surface` | the raised surface — cards, active nav |
| `--carbon-surface2` | inputs, wells, quiet fills |
| `--carbon-surface3` | tracks, hover on surface2 |
| `--carbon-hover` | row hover on the page ground |
| `--carbon-border` | hairline separators |
| `--carbon-text` / `-sub` / `-muted` | three-step text ramp |
| `--sidebar-text` | nav label colour |
| `--accent` / `--accent-contrast` / `--accent-soft` | activity |
| `--status-{ok,fail,warn,info,neutral}-{text,bg,solid}` | states |
| `--elevation`, `--hairline` | the one shadow + its top light |
| `--focus-ring` | focus outline colour |
| `--radius-card`, `--radius-control`, `--radius-pill` | the shape engine |
| `--text-heading`, `--text-body`, `--text-dense`, `--text-caption` | the type scale |

Utility classes: `.glim-card` (the surface), `.glim-well` (inset grouping), `.glim-eyebrow` (small uppercase label), `.glim-num` (tabular digits), `.glim-bubble` (the shared tooltip/info bubble, `--above` when flipped), `.glim-info-icon` (the "(i)" trigger), `.glim-picker`/`.glim-picker-sv`/`.glim-picker-hue` (the embedded colour picker), `.glim-hue` (owns a rainbow position), `.glim-hue-icon`, `.glim-tint`, `.glim-tint-badge`, `.glim-tint-hover`, `.glim-page-enter`, `.glim-toast`, `.glim-fade`, `.glim-live` (pulsing dot), `.glim-shake` (a control refusing an action).

**The token names are the contract, the values are the look.** A sibling app adopts GlimStone by pointing its own components at these same names — nothing about a component's markup has to change, because every colour already flows through a token.

## Adopting GlimStone in another app

1. Copy the `:root` / `[data-theme="light"]` blocks from [`reference/tokens.css`](../reference/tokens.css) into the app's stylesheet.
2. Copy the `.glim-card` / `.glim-well` / `.glim-eyebrow` / `.glim-num` helpers, plus the base `body`/font rules and the scrollbar and focus rules, from the same file.
3. Add whatever tokens the app doesn't have yet: `--accent-soft`, `--elevation`, `--hairline`, `--focus-ring`, `--radius-card`, `--radius-control`, `--radius-pill`.
4. Replace hard-coded `rounded-lg` / `shadow-*` on panels with `.glim-card`; fill the selected nav item, tab or segment with the accent (`segBase`/`segOn`/`segOff`, see the componentry note in each app's own style guide).
5. For rainbow, copy [`reference/appearance.ts`](../reference/appearance.ts) — it's dependency-free and talks only to `document.documentElement` and its own settings object.
6. For the scroll-to-cycle `<select>` behaviour (rule 14), copy [`reference/selectScroll.ts`](../reference/selectScroll.ts) and call `enableSelectScroll()` on every `<select>` the app mounts.
7. For flag-emoji-prefixed language options (the user-owned axes, Language), copy [`reference/flagEmoji.ts`](../reference/flagEmoji.ts) and prefix each `<option>`'s text with `flagEmoji(locale.flag) + ' ' + locale.label`.
8. For the shared tooltip/info-bubble engine, copy [`reference/tooltip.ts`](../reference/tooltip.ts) and call `wireTooltips()` once at boot; use its `infoIcon(text)` for every "(i)" explanatory trigger, and set `data-tip` (or a plain native `title`, auto-upgraded on first hover) on any icon-only control that needs a hover name.
9. For any custom-colour control (accent, a rainbow palette position), copy [`reference/colorPicker.ts`](../reference/colorPicker.ts) and call `openColorPickerPopover(trigger, hex, onChange)` on a swatch's click instead of reaching for a native `<input type="color">` — see the picker bullets under "The user-owned axes" above for when the bare `colorPicker()` (no popover) is the right call instead.

Nothing else is required: component markup stays exactly as it is, because every colour already flows through the tokens.

If the app is using Tailwind v4, [`reference/tailwind-theme.css`](../reference/tailwind-theme.css) is the optional `@theme` layer that maps the tokens onto Tailwind utility classes (`bg-carbon-surface`, `text-accent`, …). Apps not using Tailwind can skip it entirely and use the custom properties directly.

## Where the per-app detail lives

This document is app-agnostic: palette, rules, the colour-mode model, componentry vocabulary. Anything that's true for only one app — its exact token names if they diverge, class prefixes, measured pixel values, quirks of a specific host UI — belongs in that app's own style guide, not here. Each adopting app keeps a short note listing only its exceptions and gating classes; if a rule shows up in both places, delete it from the app-specific one — if it's universal, it belongs here.
